Java 为什么没有C/C++的头文件

C++ 的 .h 与 .cpp：不是本质区别，是工程约定

从编译角度看，.h 和 .cpp 没有区别

文件名后缀（如 .h、.cpp、.hpp、.cc、.cxx）对 C++ 编译器没有强制语义。

也就是说：

你可以 #include 一个 .cpp 文件,原本用来承载模板库、头文件库的 .h 文件，也可以用 .cpp 来承载，然后通过 #include 来调用

你也可以在一个 .h 文件里写函数调用,把整个项目的代码可以全部写在 .h 文件里（包括 main 函数），然后直接编译这个 .h 文件（如 g++ main.h）来生成可执行程序

没有“哪个后缀只能放什么”的规定。 编译器只认文件内容，不认后缀名。

工程上之所以把 .h 和 .cpp 分开使用，是为了避免重复定义和提高编译速度，这是工程习惯，不是语言强制。

Java 没有做这个区分，而是直接采用了“混用模式”：头文件和调用文件全都用 .java 文件来承载。 换句话说，既然 C++ 里 .h 和 .cpp 承载的内容本质上没有区别，Java 就把原本放在 .h 里的内容（声明、模板等）直接合并进了 .java 文件里，统一成一种文件格式。

所以 Java 不需要头文件，不是因为它做不到，而是它的编译模型不依赖这种分离。 你需要调用另一个类时，直接使用即可，编译器会自己去类路径里找对应的字节码文件。

三、一切皆为引用的设计模式

顺着上一节“Java 的强制堆区建立对象与指针隐藏”的思路，我们继续探讨：为什么 Java 要强制所有对象都在堆区创建？ **这样设计的底层逻辑是什么？**这才是理解“一切皆为引用”的关键。

Java 中的“引用”可以理解为受限制的、安全的指针。

背景：

Java 的设计者讨厌 C/C++ 中指针的复杂和危险（指针运算、内存泄漏、野指针等）

但又想方便地管理内存、简化生命周期，而底层实现离不开“地址”的概念

解决方案：

底层用指针实现所有对象访问

语法层面完全隐藏指针操作（不支持 *、&、-> 等）

结果：

使用者不需要知道底层是指针，也不会被指针的复杂性困扰

但当使用者学习时产生疑问：“对象传递到底是怎么实现的？为什么是这样的行为？”

设计者为了解释这些现象（如对象传递、null、垃圾回收），又不得不用“指针”的原理来说明

但为了不和 C 的“指针”混为一谈，也不吓到使用者，他们给这个封装后的概念起名叫 “引用”

底层是指针，且在语法上做了屏蔽，但为了解释行为、避免误解，Java 把它叫做“引用”。

这个“一切皆为引用”的设计，直接导致了我们前面讨论的现象：

为什么 MyClass obj = new MyClass(); 可以这样写？——因为 obj 是引用（隐藏了 *）

为什么 MyClass obj; 不创建对象？——因为只声明了引用，没有 new** **创建资源并返回地址

为什么参数传递能改变原对象？——因为传的是引用（地址）

记住这个“一切皆为引用”：

在后续学习中，凡是遇到 Java 与 C++ 行为不同的地方，很多都可以追溯到“一切皆为引用”这个底层设计。

四 对于入口函数public前缀的作用的疑惑

接下来一个问题：为什么main前面还要写public？

因为入口函数肯定没有其他函数来调用它，那你写公共访问权限是干啥用的呢？

换个角度思考：

JVM调用main，且JVM是外部程序，它需要访问这个入口函数。

从访问权限的角度，JVM和你的类不在同一个包，甚至不是Java代码。

因此需要public来允许这种外部访问。

也就是说，这里的public的公共访问权限对应外部的JVM，是强调有个JVM调用它。

关键追问：JVM作为启动器，理论上可以无视访问修饰符直接调用，那写public不是多此一举吗？

答案：

技术上，你没错，JVM确实有这个能力。

设计上，Java为了保持语法规则的一致性，不允许main成为特例——所有能被外部调用的方法都应该用public标记，main也不例外。

比喻：“让上帝遵守规则。实际上上帝可以不遵守，但为了统一规范、写得漂亮，不得不让上帝也遵守规则。”

五 Java语言特性：C++真正没有的概念——项目多主类

我们把包含入口函数的类称为主类

在C++中，一个项目有且只有一个main函数。这是链接器的硬性要求——多个main会导致链接失败。

但在Java中，情况完全不同。

Java的规则

Java允许一个项目中有多个类各自包含自己的main方法。 （表现为：一个源文件中的多个类可以各有自己的main，或者多个源文件各有一个带main的类。）

疑问：这不和之前说的“程序只能有一个起点”相悖吗？

答案：不矛盾。

根本原因：编译产物的粒度不同

Java的模型

Java编译后产生的字节码文件以类为粒度，每个类都会生成自己独立的.class文件

这就让每个类（包括作为入口的主类）独立成为一个字节码文件（无论多个main方法分布在同一个源文件还是不同源文件中，入口的承载粒度始终是单个类，与编译后的字节码文件一一对应）

运行时，JVM可以选定任意一个包含main方法的.class**字节码文件（即独立的入口单元）**来执行

因为编译产生的是多个独立的文件，所以运行器（JVM）有了选择用哪个文件作为入口的可能

C++的模型

C++采用编译 + 链接的模型。

编译阶段：每个源文件独立编译成目标文件（.obj 或 .o）。

链接阶段：链接器将所有目标文件合并成一个单一可执行文件。

这个单一可执行文件，从设计上就只能有一个入口函数（main）。

因此，链接器在合并过程中，如果发现多个目标文件都定义了main，就会报“重复定义”错误，链接失败。

这不是链接器“没做兼容”或“没做优化”，而是C++模型从根本上就不支持多个入口。链接器只是忠实地执行了这个设计。

总结

Java允许“项目多主类”的本质原因：编译以类为粒度，产生多个独立的字节码文件，JVM运行时可以动态选择其中任意一个包含main的类作为程序入口。

也就是说：一套字节码文件，根据JVM选择哪个主类作为入口，就能运行出不同的程序行为。

这就解释了：为什么Java既保证了“单次运行只有一个入口”，又允许“一个项目中存在多个主类”

这与C++的“整体编译链接成单一可执行文件、入口必须唯一”的模型形成根本性对比。

JAVA多源文件项目的代码粒度取舍

之前我们讨论过：Java编译器以类为粒度，每个类独立生成一个.class文件。

这带来了一个实际好处：部分编译。

修改一个类，通常只需要重新编译这个类对应的.java文件

其他类不受影响，可以直接使用已有的.class文件

也就是说，如果每个 .java 文件只包含一个类，那么修改某个类时通常只需要重新编译该文件，从而更好地利用部分编译的优势。但这里有一个问题：类之间有依赖关系。

如果 A.java 依赖 B.java：

只修改 A.java → 只编译 A.java 即可

修改 B.java（例如修改了方法签名） → 所有依赖 B 的类（如 A）必须重新编译，否则运行时可能抛出 NoSuchMethodError

此外，部分编译还会带来代码阅读上的代价：当你在审阅某个类的调用关系时，如果被调用的类都分散在不同的文件中，就需要额外打开多个文件才能理清完整的调用逻辑。这不像在单个文件中那样一目了然。

这反映了编译效率与运行时安全之间的权衡：

只编译修改的文件（部分编译）→ 编译速度快，但可能因依赖不一致而导致运行时错误（如 NoSuchMethodError）

每次都完整重编译所有文件 → 更安全，但编译时间更长

问题的起源：物理目录的隔离

编译器默认只编译选定的单个目录下的源文件。如果所有类都在同一个目录，编译器可以直接找到；一旦拆分到多个目录，编译器就不知道去哪个目录找其他类。

这种物理隔绝带来了调度问题：不同目录下的源码文件，编译器在没有额外信息的情况下，无法跨目录自动发现和关联。

C++的解决方案：#include <> + 绑定目录

C++同样面临这个问题——当需要调用操作系统内核中存放的头文件（而非项目目录中自己添加的头文件）时，编译器默认找不到。

C++的解决方式是：

使用 #include  语法（区别于 #include “xxx”）

在编译器中手动绑定包含目录（如 -I 参数指定路径）

编译器根据绑定的目录去查找头文件

本质上：这就是C++的“跨目录调用”机制——把一个目录（如系统头文件目录）关联到当前项目中。只不过我们当时没把“目录”称为“包”。这里的核心概念就是物理目录的隔离。

Java的差异：拆分整个项目，而非仅调度外部头文件

C++通常只把外部依赖（如系统库）放到其他目录，项目本身的源码仍然集中在少数几个目录中。

而Java喜欢把整个项目拆分成多个特定的目录结构（如按照功能模块划分）。因此，Java面临的跨目录调度问题更普遍、更常见——不只是外部依赖，项目内部类也广泛分布在不同的目录中。

为了解决这种更普遍、更彻底的物理目录隔离问题，Java正式引入了包（package）与包机制。

1 包的两个概念

物理包：源文件实际所在的物理目录。

逻辑包：编译器和运行器（JVM）认为源文件所在的目录。

在没有任何声明的情况下，物理包 = 逻辑包

例如：源文件com/example/Student.java 所在的物理目录是 com/example，这就是它的物理包，也是它的逻辑包

2

包机制对应两个关键字：package 和 import

package 关键字的作用是：把当前源文件所在的物理目录，从逻辑层面上修改成另一个包

效果：

物理包（实际目录）：com/example

逻辑包（声明值）：com.example.school

编译器和 JVM 按照逻辑包去定位这个类

具体表现：

若多个源文件的逻辑包相同（例如都是 com.example.school），编译后所有 .class 文件会生成到同一个逻辑包对应的物理目录（com/example/school/）中，并且可以互相调用、共同运行。

若多个源文件的逻辑包不同（例如 com.example.school 和 com.example.office），即使它们位于同一物理根目录下，编译器和 JVM 也认为它们属于不同的逻辑边界，不会自动互相识别或共同编译运行。1必须通过 import 显式导入，2或者使用全限定名（包名.类名）才能跨逻辑包调用。

import 是包机制的另一个核心组成部分。它的作用是：导入其他逻辑包下的类，使得当前文件可以用短名（类名）而非全限定名（逻辑包名.类名）来引用

包机制的限制

编译器按照逻辑包的位置来生成和查找字节码文件，因此：

逻辑包对应的物理目录必须在文件系统中真实存在。

也就是说，包不能完全是抽象的逻辑概念。你声明的逻辑包（如 com.example.school），必须在物理上有对应的目录结构（com/example/school/），否则编译器无法放置和定位 .class 文件。

3

没有包（默认包）的情况

如果不写 package，所有类都在同一个默认包里

效果： 两个类在同一个包里（默认包），可以互相调用。

这和 C++ 很像：跨文件实例化对象时，当前文件无需重复声明目标类，只需依赖外部已有的定义（Java中为编译后的

.class文件），即可直接创建对象。区别在于：C++ 调用其他类时，需要在当前文件中通过 #include 显式包含其声明；而 Java 不需要任何显式声明，编译器会自动查找对应的 .class 文件

引入包后的情况：

引入包之后，原本跨文件默认共享的局面被打破了。类是否可见，不再取决于是否在同一个物理目录，而是取决于它所在的包以及访问修饰符。包成了一个访问边界：同包的类可以直接访问，不同包的类则需要显式授权（import）

第二个 Java 文件：逻辑包地址为 com.main

两者的逻辑包不同，因此第二个文件需要 import 导入第一个文件中的类，才能进行调用。

4 回到包级私有

Java 多态的实现与底层原理

一、回顾 C++ 的多态机制

在 C++ 中，多态（动态绑定）需要满足两个条件：

函数被声明为 virtual

通过指针或引用调用

如果没有 virtual，编译器会在编译阶段进行静态绑定，直接确定调用的函数地址。有了 virtual，编译器才会生成虚函数表（vftable）和虚函数指针（vfptr），把调用延迟到运行时。

二、Java方法天然支持动态绑定

Java 的设计不同。它的编译模型是双阶段的：

第一阶段：Java 源码编译成字节码（.class 文件）

第二阶段：JVM 加载字节码，解释执行或 JIT 编译成本地代码

在这个模型下，Java 不需要 virtual 关键字来“打破”编译时的静态绑定，因为**Java 真正的编译成机器码的阶段在运行时（第二阶段），也就是说Java 的方法调用本身就默认采用运行时绑定 **（除了 static、final、private 方法）。

不像C++ 的机器码生成在编译阶段（第一阶段），所以需要 virtual 来人为标记哪些函数要延迟绑定。

1向上转型2同名函数重写3自动动态绑定

Java 中子类重写父类方法后，是否也会产生类似 C++ 的三份函数地址（父类原方法、子类原方法、子类继承来的方法）？

如果这个前提成立，就可以确认：Java 底层在理论上可以采用了与 C++ 类似的虚方法表替换机制来实现多态。

三、验证：重写后也是三份地址吗？

在 C++ 中，虚函数重写会产生三份函数地址：

父类自己的函数地址

子类自己的函数地址

子类从父类继承来的函数地址（后被覆盖）

Java 底层也是如此：

父类虚方法表中存有父类方法的地址

子类虚方法表一开始复制父类的虚方法表

重写时，子类虚方法表中对应槽位（slot）的地址被覆盖为子类方法地址

父类自己的虚方法表不受影响

结论：Java 和 C++ 的底层逻辑是一致的，所以 Java 多态的底层逻辑与 C++ 完全一致——事实上，Java 正是套用了 C++ 虚函数表替换机制的核心思想来实现的。

四、Java 多态中的底层的替换机理：虚方法表（vtable）

Java 底层采用了和 C++ 类似的实现方式：

每个对象中隐藏着一个指针，指向虚方法表（vtable）

虚方法表中存储着该类所有虚方法（即可以被重写的普通方法）的函数地址

当子类重写父类方法时，JVM 会将子类虚方法表中对应的方法地址覆盖为子类自己的实现

这个过程和 C++ 的虚函数表机制本质完全一样，只是 Java 换了个叫法：虚方法表。

五、JAVA自动动态绑定机理造成的多态使用表现

Java 完整实现了向上转型、虚方法表替换、动态绑定等一系列多态所需的底层机制。

由于动态绑定在 Java 中是自动生效的（不需要像 C++ 那样用 virtual 关键字主动标记），所以：

想要实现多态，只需要两个条件：

子类重写父类的同名方法

通过向上转型（父类引用指向子类对象）调用该方法

不需要任何额外关键字来“开启”动态绑定。

这意味着在 Java 中，一个普通方法（非 static/final/private）：

原本只是普通方法

一旦被子类重写，并且通过向上转型调用

它就自动具备了虚函数的特性：运行时动态绑定、调用子类版本

换句话说：

Java 的普通方法，在“被重写 + 向上转型”后，就从普通方法“变身”为可以实现多态的虚函数。

因此 Java 不需要像 C++ 那样专门设置“虚函数”这个名词——因为除了 private、final 和 static 方法之外，所有普通方法默认就是虚函数。 只有“纯虚函数”（C++ 中 virtual void f() = 0）才需要 Java 创建“抽象方法”这个名词来对应。

匿名类

这是匿名类的核心语法——在创建对象的同时，直接在后面跟上一对大括号 {}，在大括号内重写父类的方法。

普通的对象创建是 new 类名();，分号表示结束。而匿名类把分号换成了 {}，在大括号里完成方法的重写或实现，最后再补上分号。

C++ 和 Java 的“匿名类”不是一回事

C++ 也有一个“匿名类”，但和 Java 的同音不同义。Java 这里的匿名类是 C++ 没有的内容。

在教科书上，匿名类也通常被叫做匿名子类——因为它一般用于重写父类或接口的方法，干子类干的的活。

但问题是按照匿名类是子类来理解：这个匿名子类没有名字，无法单独创建对象，所以它只能和父类/接口绑定在一起，从头到尾仅有一个父类对象被创建了。

从“只能和父类对象绑定”这个位置关系来看：

它不像是传统意义上的独立子类——传统子类是“先定义子类，再创建子类对象，子类对象和父类对象是两码事”。

而匿名类是：new 父类() { … }——你只有父类的引用，子类没有名字、没有独立存在。它更像是一个替换了子类功能的内部类，直接附着在父类对象上。

为什么可以说是“

替换了子类功能的内部类”�，内部类也能实现子类的活

当外嵌类的方法是抽象方法或者普通方法时，内部类又继承于外嵌类,就能重写抽象方法或者普通方法：

而且匿名类还有普通子类做不到但是和内部类能做到的功能：可以访问被寄生类（外嵌类）的私有成员（内部类才能实现）,所以匿名类实现内容的和有继承的内部类是一样的，而子类无法实现匿名类的”访问私有内容”的功能 所以说匿名类就是一个（实现继承的）内部类

那为什么匿名类在教科书上常被称为“匿名子类”呢？

这是因为从功能上看，它最常用于重写父类或接口的方法，行为上像子类。教材只强调其“子类”特性，是因为“继承外嵌类的内部类”这个概念较复杂，为降低门槛，教材从最直观的功能出发将其简化为“匿名子类”。

但从本质上看，匿名类并不是传统意义上的子类。 传统子类是独立存在的类，通过 extends 继承父类，与父类是两个独立类型。而匿名类必须定义在外嵌类内部，持有对外嵌类实例的引用，能访问其私有成员——这些特征全部来自“内部类”身份。

因此，更准确的定义是：

匿名类本质上是一个“继承了外嵌类的内部类”。

它与普通子类的本质区别在于：普通子类只有继承关系，没有内部类的访问能力。

异常类与抛出接住机理

一、什么是异常类？

异常类就是继承自 Exception 或 RuntimeException 的类（也可以是这两个类本身）。

为什么必须是它们？因为异常类的用途是抛出异常——即发生错误时，向外发出报警信息。

Exception 和 RuntimeException 这两个基类自带了一个关键方法：printStackTrace()，用于输出堆栈信息。JVM 或 catch 块收到异常后，需要调用这个方法输出报警信息。所以，只有继承自它们的类，才能保证 JVM 能正确调用这个方法，才能叫做异常类。

RuntimeException 是 Exception 的子类，那为什么还要把两者并列来介绍呢？

因为 Exception** 类本身及其所有子类（除了 RuntimeException 及其子类）都属于受检异常**。也就是说，Exception 这个分支下，实际上分为两派：

一派是 RuntimeException 及其子类（非受检异常）

另一派是 Exception 的其他子类（受检异常）

我们之所以把两者并列引出，就是为了先讲清“继承关系”，为后面区分“受检异常”和“非受检异常”打下基础。

下面我们先讲简单的异常类（即非受检异常，如 RuntimeException 及其子类）作为前提。

二、抛出的信息是什么？

抛出的是一个指针（即异常对象的地址）。

三、抛出后谁接收？——两种情况

情况一：被 try-catch 接住

catch 的参数列表是 异常类类名 对象名（这里的对象名本质上也是一个指针，Java 隐藏了 *），正好和抛出的指针类型匹配。

情况二：没被接住

如果异常抛出后没有被任何 catch 接住，就会传给 JVM，由 JVM 处理。

四、接住后如何发出警报？

1 JVM 收到未捕获的异常后，会做两件事：

调用异常对象的 printStackTrace() 方法，输出堆栈信息（这就是为什么异常类必须继承自 Exception 或 RuntimeException——保证这个方法存在）

调用 exit() 方法，结束程序运行

2 如果是 catch 接住了，你可以：

主动调用 e.printStackTrace() 输出堆栈信息

主动调用 System.exit() 结束程序

写异常修正逻辑，不输出、不退出，让程序继续运行

当代码运行时发生运行时异常（RE），JVM 会：

自动创建一个默认的异常类对象（如 NullPointerException、ArithmeticException 等）

六、受检异常与throws

throw 与 throws 的区别

受检异常（Exception 及其子类，不包括 RuntimeException）有一个硬性规定：要么被 try-catch 接住，要么在方法上写 throws 声明。

如果你写了 throw new Exception(“…”) 但既不加 try-catch，也不加 throws，编译直接报错——这不是运行时问题，是语法错误。

为什么受检异常必须被处理（try-catch 或 throws）？

核心原因：受检异常就是用来防止你忘记处理的异常。

如果你既不用 try-catch 接住，也不写 throws 声明（表示“我看到了，但我不接”），那就说明你可能根本没意识到这个异常的存在——这恰恰失去了“受检”两个字的意义。

所以编译器强制要求：要么你主动接住（try-catch），要么你明确声明“我看到了，但我不处理，交给上层”（throws）。

throws 的向上级丢锅，最终到JVM

throws 的意思是：这个异常我看到了，但我不在这里用 try-catch 处理，我把它抛给调用我的方法。

这里我们的受检异常被抛出，且没有用 try-catch 接住，所以它会根据 test() 方法后面写的 throws，向上抛给调用它的方法。

调用它的方法面临同样的选择：

要么用 try-catch 接住

要么继续写 throws，再往上抛

就这样一层一层往上抛，直到 main 函数。

如果 main 函数也写 throws 而不接住，那么异常最终就传给了 JVM，由 JVM 来处理（打印堆栈信息并退出程序）

二 根据类名动态创建对象（实例化）

正常情况下，创建一个对象是用 new 类名()，比如 new String(“Hello”)。但 new 有一个限制：类名必须在编译时就确定，写死在代码里。

第三步：通过构造方法对象真正创建出实例

方式一：通过 对象.getClass() 获取

虽然每个类被加载到内存后，JVM 都会为其创建一个唯一的 Class 类型的实例（即 String.class 这个类级对象），该实例无需创建 String 对象就已经存在——它是类级别的，在类加载时就已经产生。但问题是：getClass() 是一个成员方法，必须通过对象来调用。即便 Class 对象本身已经存在于内存中，我们也无法直接通过类名调用 getClass()。这意味着必须先创建目标类的一个对象，才能通过这个对象调用 getClass() 拿到 Class 对象——这显然与”根据类名动态创建对象”的初衷相矛盾：我都还没有对象，怎么用 getClass() 去拿？拿了就是为了创建对象的呀。

方式二：通过 类名.class 获取

这种方式不需要创建对象，因为 class 是类级的静态成员，类加载到内存后就已经存在。但它的局限性在于：类名在编译时就必须确定，无法做到运行时动态传入。

方式三：通过 Class.forName() 获取

Class.forName() 的优势在于：

不需要先创建对象——它是静态方法，类级调用，无需实例存在
