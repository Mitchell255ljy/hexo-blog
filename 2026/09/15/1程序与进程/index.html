4T01 程序与进程

发表于2026-09-15|更新于2026-09-21
|浏览量:

计算机科学中一个常见问题是：我们如何称呼 CPU 执行的所有活动？

很多人会认为是“程序”，但在计算机科学中，更准确的说法是“进程”。

在操作系统中，程序的一次执行过程被抽象为进程。进程具有一定的生命周期，通常包括创建、就绪、执行、阻塞和终止等状态。换言之，进程是正在运行中的程序。

程序则是为了完成特定任务而组织起来的一系列指令和数据的集合。它是静态的，没有生命周期，通常以二进制文件的形式存储在磁盘等外存设备上。如果仔细分析上述描述，会发现它同样可以用来描述一个可执行文件——这是因为程序基本上正是如此。

理解了程序和进程的区别后，我们来看进程在内存中的表现。在计算机组成原理中，程序运行后产生的内存布局，实际上就是进程在地址空间中的表现。

假设我们用同一个文本编辑器阅读两个文本文档。同时打开这两个文件时，操作系统会为该文本编辑器创建两个进程，于是产生两个独立的窗口，分别显示不同的文本文件。它们来自同一个程序，却是两个不同的进程。

每个进程都拥有独立的虚拟地址空间。尽管两个进程中的代码段（TEXT）内容相同，因为它们来自同一个程序，但它们处理的数据段（data）、堆（heap）和栈（stack）是彼此独立的。图中第一个进程占用的地址空间更大，是因为它处理的文本文件更大，需要更多内存来管理相关数据。

不过，以上讨论主要适用于编译型语言。使用 C 或 Rust 等语言时，编译结果通常是一个可执行文件，也就是程序本身。

解释型语言则不同。以 Python 为例，源代码通常不会编译成独立的机器码可执行文件，而是由解释器在运行时加载并执行。每次运行 Python 代码时，实际启动的是 Python 解释器进程，解释器再读取并执行我们的源代码。

因此，这里涉及两个不同的对象：一个是 Python 解释器，它是一个程序；另一个是 Python 源代码文件，它本质上是一个文本文件。由于解释型语言通常不生成独立的可执行文件，运行时实际被启动的程序是解释器，而不是我们编写的 Python 源代码。

解释器进程创建后，会拥有自己的进程地址空间，与其他进程一样。解释器会在自己的地址空间中构建运行时环境。具体来说，解释器加载的源代码或编译得到的字节码、运行时创建的对象和数据，通常分配在堆区；解释器自身的函数调用、局部变量和返回地址等，使用真实的栈区。代码区和全局区则分别存放解释器自身的机器指令和全局状态。

在解释器内部，还会维护一套用于执行源代码的运行时结构。这些结构在逻辑上承担了类似代码区、全局区、堆区和栈区的职责，但它们并不是操作系统意义上的独立内存区，而是解释器在自身进程地址空间中维护的数据结构。

具体来说：

模拟代码区由字节码和代码对象承担。字节码是解释器真正逐条读取的“指令”，代码对象则是对字节码的包装，里面还包含常量表、名字表、栈大小等信息。字节码和代码对象本身分配在堆区，但它们在逻辑上扮演“指令”的角色。模拟全局区由全局名字空间和内置名字空间承担。全局名字空间本质上是一个字典（键值对集合），用来存放模块级变量、函数名、类名等。它本身是堆区里的一个对象，可以增删键、可以扩容，但它始终承担“存放全局名字”的职责，所以全局区的稳定性来自逻辑职责的固定，而不是物理地址的不变。模拟堆区由动态对象、实例、容器以及对象分配器承担。这部分本来就是堆区自身的东西，所以堆区扮演堆区，属于本色出演，不需要额外模拟。模拟栈区由栈帧、求值栈和调用链承担。栈帧本身是分配在堆区里的对象，但它们按后进先出的规则使用：调用函数时压入新栈帧，函数返回时弹出栈帧。求值栈同样分配在堆区，用来存放字节码执行过程中的临时值。因此，栈区的“栈”不是物理上位于真实栈区，而是逻辑上按栈规则使用堆区里的对象。

解释器真正的代码区中有一个主循环。这个主循环从模拟代码区中取出下一条字节码，跳转到对应的机器指令去执行。执行过程中，会根据字节码的需要，读写模拟全局区、模拟堆区和模拟栈区。因此，源代码能够运行，依靠的是解释器在自身进程地址空间中构建的这套运行时环境，而不是堆区本身变成了代码区。真正执行机器指令的是解释器的代码区，但被解释的“指令”来自解释器维护的字节码结构；解释器自身的函数调用使用真实栈区，而 Python 层面的函数调用由解释器维护的栈帧结构表示。二者分属不同层面，不应混为一谈。

我们这里开始介绍批处理的概念，以便引出现代操作系统处理任务以及进程演化而出的过程。

你可能接触过 .bat 文件。比如一个 bat 文件内写一行 start 链接，保存好双击运行，我们就能看到一个黑屏（cmd 窗口），然后它消失，你的链接指向的地方就被打开了。

在 Windows 里的 .bat / .cmd，叫 batch file，中文译作“批处理文件”。它的本质是把一堆命令写在一个文件里，由命令解释器（cmd.exe）一条接一条顺序执行，不需要你每条都手敲。也就是说，批处理文件就相当于帮你做了一个把 cmd 终端的命令保存下来、双击向 cmd 终端自动写入回车的一个文件。所以它叫“批处理”，是因为把一批命令集中起来处理。这一层只关乎“命令的批量执行”，跟操作系统怎么调度、有没有进程概念，基本无关。严格说，这更应该叫命令脚本或 shell 批处理。

而我们要讲的批处理，是把一批命令集中起来去处理的概念，而不是仅仅是一个执行这个概念的 bat 文件。那么这种思想下，我们还会涉及两个东西：批处理系统和批处理进程。

早期的计算机是批处理系统，它们执行被称为“作业”的工作单元。批处理操作系统确实是早期（大型机时代）的 OS 形态，那时还没有现代意义上的“进程”概念，调度单位是作业。它是操作系统的类型或运行模式：作业成批提交、脱机/半脱机、无交互、以吞吐量为目标。但是这样用户不能干预作业运行。

为了打破这种“提交后只能等”的限制，所以人们开发出了分时操作系统。

分时操作系统允许多个用户通过终端同时连接到同一台计算机，并交互式地使用计算机资源。它的核心目标是公平、高效地服务多个交互式用户，让每个用户都感觉自己“独占”了计算机。这里的用户就是人。分时系统把 CPU 的时间划分成很短的时间片，轮流分配给各个用户的作业。由于切换速度极快，每个用户都感觉自己的请求得到了即时响应。这背后其实是两个独立的需求：

一是多用户：多个用户的任务要同时在系统里存在，轮流上 CPU。这逼出了时间片轮转和并发调度。

二是实时响应：用户敲下命令要立刻得到反馈，任务不能占着 CPU 傻等。这逼出了阻塞/唤醒机制——任务在等输入时让出 CPU，输入到了再被唤醒。

这两个需求共同要求一个可保存、可恢复、可隔离的执行流抽象。时间片轮转需要执行流能被中断、保存、恢复；实时响应需要执行流能被阻塞、唤醒、隔离。作业模型给不了这个抽象——作业是整体性的工作单元，只有整体状态，没有执行流状态。于是进程（process）这个概念被正式提出。进程是“程序在数据集上的一次执行活动”，是操作系统资源分配和调度的基本单位。用户通过终端启动的每个任务，对应一个进程。

进程概念的核心意义，是把“程序本身”（静态代码）和“程序的执行过程”（动态活动）区分开，让执行过程可以被中断、切换、调度，从而适配分时系统快速切换和资源隔离的需求。它的思想萌芽在批处理系统中已经出现，但真正系统化是在分时系统阶段。1963 年，MIT 的 CTSS 分时系统开发中，Marvin Conway 正式提出进程概念，将其定义为“程序在数据集上的一次执行活动”。

分时系统的并发、时间片、阻塞/唤醒，原本是为多用户共用一台机器设计的。随着硬件成本下降、计算机走向个人使用，这套机制也普及到个人计算机上，变成了单个用户也能同时运行多个程序、交互式处理各类任务的系统。

现代操作系统的雏形就在这里出现了。而进程这个抽象一旦确立，就被用来统一承载所有任务，原来“成批、非交互、后台跑”的那类任务，在现代进程模型里归为批处理进程。换句话说，批处理进程不是“用户”，而是进程按行为特征划分出来的一类：非交互、后台、吞吐导向。它继承的是早期批处理系统的“作业”特征，但调度单位已经是“进程”。

所以这条演化线是：

批处理操作系统（作业级、系统级） → 分时系统为“多用户 + 实时响应”引入时间片、并发与阻塞/唤醒 → 两者共同逼出进程抽象，进程成为统一的调度单位 → 现代 OS 用进程承载所有任务，其中非交互、后台、吞吐型的一类被称为“批处理进程”（进程级的一类）

那么，进程作为统一调度单位，到底是怎么被操作系统调度起来、让多个任务看起来“同时推进”的？这就涉及一个核心概念：并发。

并发指的是多个任务在时间上重叠推进。在单核 CPU 上，任意一个时刻真正在跑的只有一个任务。操作系统把 CPU 时间切成很短的时间片，轮流分配给各个任务：任务 A 跑一小段，切换到任务 B，再切换到任务 C，再切回任务 A。因为切换速度极快，从外部看，这些任务就像在同时推进。

分时系统用的就是这种并发模式。它只有一颗 CPU，靠时间片轮转制造出“多个用户同时使用”的效果。每个用户的任务跑一小段就让出 CPU，下一个任务接着跑，如此循环。

这里要先区分一个容易混淆的词：并行。并行指的是多个任务在同一时刻真正同时执行，这需要多个 CPU 核心或多个处理器。比如四核 CPU 同时跑四个计算任务，这是并行。并行可以看作并发在多核上的扩展：单核靠时间片轮转制造“同时推进”的观感，多核则可以让多个任务真正同时跑。不过并行涉及多核调度、缓存一致性、核间通信等更多问题，这里先把单核上的并发讲清楚，并行放到后面再展开。

回到并发。任务 A 让出 CPU 之后，它跑到哪了？下次切回来，它怎么知道从哪继续？任务 B 会不会踩到任务 A 的内存？这些问题的答案，就是进程。并发调度要求每个任务都有自己独立的执行状态和资源边界，能被中断、保存、恢复、隔离——这正是进程要提供的东西。

所以，并发是分时系统“多任务同时推进”的实现方式，进程是并发调度得以成立的基本单位。理解了并发，才能理解为什么操作系统需要进程。

并发不是一句“轮流跑”就能说清的。它落到操作系统底层，要回答一连串具体问题：时间片是谁在切、切换时执行流的状态保存在哪、下一个任务由谁挑、等待中的任务又怎么被唤醒。下一章我们就从这些底层机制入手，看看操作系统究竟是怎么把“并发”这件事真正做出来的。
