声明 定义 调用

注意 同一名字的声明是可以在单文件内重复出现的

编译器规定调用前必须有声明，因为编译器逐行从上到下读取。

如果声明在调用后，就会导致出现“调用空气”的概念。

函数于变量在单文件下的调用规则

一般的函数和变量不需要单独的声明语句。对于函数而言，如果定义写在调用之前，编译器视为定义即声明,而先调用后定义,则需要再调用之前写上声明;对于变量而言，在单文件内，定义即存在，不存在脱离定义的“爸蒙�”枨螅恢挥性诳缥募猛獠勘淞渴保判枰柚� extern 丶纸�“�”�“ㄒ�”邪氤隼础�

根本原因是函数可以通过函数名是否后接 **{具体实现内容} **(花括号和实现) 来区分定义和声明,

但是变量没有实现部分的构造 所以不支持定义和声明的区分

注意 因为函数的定义大部分的内容是函数的实现 所以在语义上 “函数定义” 和 “函数实现” 几乎是可以互换的同义词

借用头实现跨文件下的函数与变量调用

如果我们想要把一个文件下的M个函数的实现 能被N个同一项目下的源文件调用

是不是每个文件都要M个函数的声明 那么一共要写N*M遍声明 这显然太麻烦了。

借助 预处理指令#include 的文件内容插入机制(复制粘贴)，将 M条声明集中放入一个头文件，每个源文件只需一行 #include 即可引入全部声明，总代码量从 N*M行压缩至 M 行声明加 N 行#include包含指令。

利用include头文件复制声明到多文件实验.cpp里面了

这个用一个.h写声明一个.cpp写定义,来实现跨文件调用的模式 就是后面 库 要讲的 基础分离模型/传统分离式

编译与链接

多个源文件—>编译—>链接—>可执行文件—>运行

编译阶段产生机器码 不看实现仅看声明

链接阶段处理机器码 把声明和实现链接起来 找不到实现是链接器报警

运行阶段执行机器码 可执行文件exe就是全机器码

在同一项目下，多个源文件最终会被链接成一个可执行程序。既然链接阶段会把所有实现拼合到一起，为什么编译器还要求我们在每个文件里提前写声明？这不是多此一举吗？

因为编译和链接是两个完全独立的阶段，编译器在编译单个文件时，根本看不到其他文件的内容，假如说多文件项目A文件写了实现,B文件想要调用该实现,因为编译器的局视性B文件要是不写声明 编译器就会认为 �GB文件怎么没写声明就调用啊(编译器逐个审查单文件 它不知道别的文件里写了实现 但是因为下一步的链接器会把这些文件链接到一起肯定是互通的,编译器为了处理这种实现在别的文件 但是又要保证自己的纠错功能 做出了让步 单个文件下可以不写实现 但是一定要有声明才能调用)。

编译器的视野被严格限制在当前正在处理的这一个 .cpp 文件内。它不允许、也没有能力去翻看其他 .cpp 文件里写了什么。

声明是给编译器的承诺，定义是给链接器的兑现。

编译器在编译当前文件时，视野被限制在这一个文件内，它需要声明来”认识”外部的函数。链接器则负责在全局范围内寻找这些声明的真身，把它们拼成完整的程序。

这就是为什么跨文件调用必须写声明——不是多此一举，而是分离编译机制下的必然要求。

库

1 全局函数前加 inline 后，当它被多个 .cpp 文件通过 #include 复制多份定义与实现时，链接器看到 inline 关键字，会知道这个函数允许存在多份定义，只取其中一份，而不会报“重复定义”错误。

2

头文件中写类不怕多次#include导致重定义,需要从两方面讨论：

第一方面：类本身及其成员变量的声明

类在编译后不会进入任何内存区（只是编译时的蓝图）

因此多个 .cpp 包含同一份类定义时，链接器根本看不到它 → 不会产生重定义问题

第二方面：类内直接实现的成员函数

成员函数是真正的代码，会被写入代码段

按理说多个 .cpp 包含会导致重复定义

但 C++ 规定：类内直接实现的成员函数隐式带有 inline 关键字

inline 告诉链接器：允许重复定义，你只取一份即可 → 所以也不会重定义

这里的Header-Only库 又称 头文件库

头文件库的实现与调用

传统分离式（对应SDK 模式）

头文件（.h）：只写声明（函数原型，变量加 extern）。

源文件（.cpp）：写实现（函数体）。

多个源文件包含这个头文件时，各自只拿到声明，编译通过。链接时，所有调用方都指向唯一的那份实现。

这跟 SDK 库的思路其实是一样的：把具体的实现藏到别的地方，只在头文件里留下外部声明。 这样一来，项目里需要用到这些功能的地方，只要包含一下头文件就能调用，而不用关心实现到底在哪——实现跟项目本身就这样干净地分开了。

dll / lib 里写实现

.h 头文件写外部声明

使用时 #include 头文件即可

但是这样在每个项目的时候都要包含两个文件 一个.cpp 一个.h 这样太麻烦了 我想要简单无脑一些 把实现和声明都写进一个.h里 包含一个文件就行

头文件库(即Header-Only库,对应模板库)模式

如果非要把实现写在头文件里，还想让多个源文件安全包含不会发生链接时重定义，就需要写模板库——把函数写成函数模板，利用模板的”模糊链接”机制让链接器自动合并重复定义。

模板的构成：由 template  修饰的类模板和函数模板组成（如  所示）

工程替代方案（仿模板库/也就是Header-Only库）：如果模板语法过于复杂，可以用 inline + class 封装，实现同样的“头文件内部写实现”效果。

inline** 把函数从“强符号”变成“弱符号”。链接器遇到多个同名弱符号时，不报错，随便选一份保留，其余扔掉。这就是 inline 应对链接器的核心机制。**

头文件库的实现原理

链接阶段就是处理编译阶段产生的机器码的阶段

因为类定义本身不产生机器码/符号，所以链接器根本看不见它，自然不会因为它在多个文件里出现而报错。

类定义只是蓝图,不产生机器码,链接器看不见。

只有用类定义创建对象时,才产生机器码,链接器才能识别到这些对象。

如果多个文件里创建了同名的全局对象,链接器就会因为重复定义而报错。

成员函数作为独立的机器码存放在代码区，为了防止定义在头文件时引发链接冲突，C++规定类内定义的成员函数自动成为 inline 函数，让链接器可以安全地合并重复的机器码。自动内联就是前面接inline

静态static

static

的本质：作用域内唯一

static 的核心含义是：在它所属的作用域内，只有一份。

它和 extern 正好相反：

extern：告诉编译器“这个东西在别处”，作用是跨作用域共享

static：告诉编译器“这个东西只在这里”，作用是作用域内唯一

一、文件作用域（全局变量/函数）

作用域：当前 .cpp 文件

唯一性：其他文件没有，也不能通过 extern 找到

效果：隔离（不共享）

extern 的对立项就在这里：extern 说“找别的文件”，static 说“只在这个文件”。

二、类作用域（静态成员变量/方法）

作用域：整个类

唯一性：这个类的所有对象共用这一份

效果：共享（共性）

这里的 static 不是隔离，而是让所有对象共享——因为作用域是“类”，类内只有一份，所以对象之间自然共享。

三、函数作用域（静态局部变量）

作用域：函数内部

唯一性：所有对这个函数的多次调用共用这一份

效果：共享（值跨调用保持）

普通局部变量每次调用重新创建，static 让它在函数作用域内唯一，所以值会一直保留。
