软件开发工具包SDK

SDK库的组成部分声明和实现的表现形式为,一套写好声明的.h,一套放实现的.lib/.dll

SDK 到底封装了什么

普通库：封装数据结构 + 算法

所谓的普通库就是：头文件库、模板库、传统分离模式

SDK：封装带系统资源的复杂活对象（平台SDK/部分扩展SDK），或封装复杂逻辑/算法/状态机（扩展SDK）

平台 SDK与扩展sdk

平台 SDK，最初就是配合操作系统内核资源（文件、网络、进程）功能实现的 SDK。早期的平台 SDK，绝大部分就是面向系统资源的实现。所以后来它也叫做内核 SDK——操作系统层的功能实现，都是说“去调用内核 SDK”。

扩展 SDK则不同。它有的涉及内核扩展，有的是纯逻辑，有的调用系统内核资源，有的不调用。但即使它涉及内核资源，也不叫内核 SDK。

为什么？

因为内核资源只能由官方的 SDK 调用。扩展 SDK 要去调内核资源，实际上必须经过内核 SDK ,这是因为操作系统内核在设计时，就明确规定了只有自己提供的特定DLL(平台sdk)（如ntdll.dll、kernel32.dll）内部的那个syscall指令是合法入口,而扩展sdk没有那个“直接作为唯一入口”的地位

SDK库实现文件的连接原理

SDK库的实现存放在以.lib/.dll为后缀名文件中 而普通库把实现写道.h和.cpp文件种

一、普通库（头文件库/模板库/传统分离模式）的实现调用流程

1. 实现放在当前项目里

模板库：实现写在 .h 里

传统分离：.h 声明 + .cpp 实现

头文件库：实现全部写在 .h 里

2. 编译阶段

实现的源码（.cpp 或 .h 里的实现）参与编译

源码经过编译器转成机器码（.obj 或 .o）

3. 链接阶段

把转好的机器码链接到一起，生成 .exe

本质：实现的源码 → 编译阶段转机器码 → 链接

二、SDK库的实现调用流程

1. 实现不在当前项目里

你只拿到一个 .h 头文件（里面是声明）

实现藏在 .lib 或 .dll 里

2. 编译阶段

你 #include 这个 .h 头文件

编译器只看到声明（比如 void func(void);）

编译器不检查实现是否存在，看到声明就放行

没有实现也不会报错

关键：编译阶段，SDK的实现（.lib/.dll里的代码）完全没有参与

3. 链接阶段

链接器去找 .lib 文件 并区分 .lib 的类型：

①静态库（.lib 里是功能实现的机器码）→ 链接器把机器码复制进最终可执行文件，运行时不需要 .dll** **

这种链接方式：称为静态链接

②导入库（导入库.lib 里存放的是导入描述符，不是机器码）→ 链接器在最终可执行文件里，根据导入库中的导入描述符和调用情况，生成导入表。运行阶段时导入表被映射到内存中，负责把.dll导入到内存中

导入描述符的生成与对接规则： 导入描述符的具体生成方式，以及它如何与 .dll 的导出表（即二进制接口）完成对接，将在后续章节详细说明。本节仅需理解：导入描述符是导入库（.lib）的核心内容，链接器根据它和调用情况生成导入表；而导入表与导出表的成功匹配，是运行阶段 .dll 能够被加载和调用的关键前提。

这种链接方式称为：动态链接

4. 运行阶段

静态链接的情况：可执行文件里已经有全部机器码，直接执行lib机器码，不涉及 .dll

动态链接的情况：操作系统加载器读取可执行文件里的导入表，把对应的 .dll 加载到内存，然后执行 .dll（.dll 是功能实现的机器码） 里的机器码

操作系统的加载读取对应表现就是.exe旁边放.dll文件就能让可执行文件调用.dll里的功能实现

三、根本原因

为什么SDK的实现文件不参与编译阶段？

因为 .lib 和 .dll 本身就是机器码。

你用记事本强行打开 .lib 或 .dll，看到的是

全是 0101010 这样的二进制数据

它们不需要再经过编译阶段转机器码，因为已经是机器码了

而普通库的实现最初是源文件（.cpp、.h 里的模板代码），必须在编译阶段由编译器转成机器码。

链接器链接静态链接库操作

刚刚讲了**.lib的两种类型和.lib与.dll的关系**

.lib** 是链接阶段用的（静态库或导入库）**也就是说SDK调用实现链接阶段必须有.lib 当 .lib 是导入库时, .dll 是运行阶段用的（动态链接库）

我们现在来学习VS链接器链接.lib的具体操作

默认库列表负责提供需要链接的库文件名

链接器内部维护了一个默认的库列表（包含大部分平台 SDK 的 .lib ,少部分平台SDK）。链接阶段本质上是解析未定义的符号、寻找其实现。当源文件调用了某个 SDK 函数时，链接器(就会寻找对应实现)会从默认库列表中查找对应的 .lib。

但扩展 SDK 以及少数平台 SDK 的 .lib 不在链接器的默认列表里。而不在该列表中的静态链接库比如sapi.lib需要调用comment指令。

VS 支持 #pragma comment(lib, “xxx.lib”) 指令。这个指令会在编译生成的 .obj 文件中写入一条记录，链接器读取到该记录后，会将该库追加到待搜索的库列表中（效果等同于把它加入默认库列表）。

默认库目录列表负责提供搜索这些库文件时的目录路径

在 Visual Studio 中，默认库列表仅包含库文件名，不包含路径信息，链接器需结合默认库目录列表逐一搜索以定位库文件。即使是平台 SDK 的 .lib 文件，链接器也需要按照默认库目录列表一个一个找。

一般来说我们不会把.lib文件放到默认库目录列表当中

这意味着，即使你在代码中通过 #pragma comment(lib, “xxx.lib”) 指定了库文件名，链接器仍然找不到这个 .lib，因为它不会主动去项目根目录下搜索。

这时需要向附加库目录（项目属性页 → 链接器 → 常规 → 附加库目录 → 计算的值）填入指定的库目录，来实现额外添加的 .lib 文件。

但注意：无论你把库目录添加到“附加库目录”还是“默认库目录”，底层逻辑完全一样——附加库目录的内容最终都会被合并到默认库目录里，一起传给链接器。

区别只在于 UI 和维护性：

写在默认库目录里：系统自带路径和你自己添加的路径会混在一起，时间久了分不清哪些是原来的、哪些是你加的，想删除或修改容易搞混。

写在附加库目录里：这个界面只显示你自己添加的路径，和默认库目录的信息完全分离，一眼就能看出哪些是为当前项目额外加入的。

因此，虽然底层两者是合并的，但推荐写在附加库目录里，这样既能让链接器找到库，又能保持配置清晰、便于维护。

写在附加库目录里 = 底层和默认库目录合并，但 UI 上分离开，让你看得清哪些是自己加的。

写在默认库目录里 = 底层效果一样，但 UI 上混在一起，分不清哪些是原来的。

最佳实践是把需要的 .lib 文件放在项目根目录（或根目录下的 lib 子目录）中

把 .lib 文件放到项目根目录（或 lib 子目录）里。

因为这样 .lib 和项目绑定在一起

点击生成后，在对应目录中只看到 .dll 文件，没有配套的 .lib 文件。

原因： DLL 默认不导出任何函数。没有导出，链接器就不会生成导入库（.lib）。

导出和导入库的生成是同时、伴生的。导入库里存放的导入描述符，就是 DLL 中所有被标记为导出的实现的记录表

因为EXE和DLL是两个独立的文件（有边界），所以DLL内部的代码默认对外不可见，这就为“隐藏实现”提供了前提。

为此，DLL的设计者规定：在编译DLL时，如果想让外部EXE调用某个函数，就必须把这个函数名写入DLL的“导出表”（比如用__declspec(dllexport)），这个写入动作就叫“导出”。

同时，编译DLL还会附带生成一个.lib文件（导入库），里面存放了刚才导出的那些函数对应的导入描述符（记录着函数名、所在DLL名称等信息）。

至此，SDK的构建阶段结束。

当进入SDK调用阶段，调用SDK对应的.lib并编译生成EXE时，链接器会根据.lib文件中的这些导入描述符，在EXE内部生成**”导入表”**（即把导入描述符实例化到EXE的结构中）。这张导入表就像一张”白名单”，只允许EXE去调用那些有导入描述符记录的函数。

当EXE运行时，系统再根据导入表去DLL的导出表里寻找对应的函数地址，找到后连上线完成调用，这个运行时连线的过程才叫真正的”导入”。

反过来，如果DLL内部某个函数没有被标记为”导出”（比如仅供内部使用的辅助函数），那么它就不会出现在导出表里，配套的.lib文件中也不会有对应的导入描述符。当EXE尝试调用这个函数时，链接器翻遍.lib文件都找不到对应的导入描述符，因而生成不了导入表项，链接器就会报错（无法解析的外部符号），根本生成不了EXE文件，更别提运行时调用了。

DLL**默认隐藏所有实现(导出表默认无接口信息)，**只有明确标记“对外开放”的函数，才会被写入导出表。

下面我们就开始讨论导入操作和导入操作的具体实现

如何规定dll中的实现接口的开放和隐藏 导出关键字

在SDK库编译前的头文件（.h）中，通过__declspec(dllexport)关键字进行导出标记。

在 SDK 库的编译前阶段，头文件中加入 __declspec(dllexport) 导出关键字，并在实现文件（.cpp）中包含(include一下,这也是不同于静态库编译前没进行include的操作的操作)该头文件。这样做的目的，是将头文件中声明的函数标记为需要导出，从而避免在每个函数实现前重复书写 __declspec(dllexport)。

如果开发者选择不在实现文件中包含头文件，则必须在每一个需要导出的函数实现前手动添加 __declspec(dllexport)。

无论采用哪种方式，只要至少有一个函数被标记为导出，链接器就会生成对应的导入库（.lib）。

在SDK库的编译后阶段,根据导出关键字的标记,在生成的装载功能实现.dll文件中,被标记导出的实现会在.dll内的导出表内产生实现对应的接口(二进制接口)，为了以后的调用阶段做配对

如何对接dll导出表中的实现接口(二进制接口) 导入关键字

在调用cpp编译前的头文件（.h）中，通过 __declspec(dllimport) 关键字进行导入的标记。

用户在调用 .dll 内部的实现时，需要在头文件（.h）中使用 __declspec(dllimport) 对函数进行声明，以表明该函数是外部导入的。

在链接阶段，链接器会根据该导入声明，去查找对应的导入库（.lib）中的导入描述符：

如果导入库中存在该实现的导入描述符，那么链接器就会将这个函数调用加入到最终可执行文件（.exe）的导入表中。

如果导入库中不存在对应的导入描述符，那么链接将失败，并报出 unresolved external symbol 错误，该调用不会被加入导入表。

在运行阶段，操作系统加载器会根据可执行文件中的导入表，去加载对应的 .dll，并调用其导出表中的实现接口（即二进制接口），从而完成函数的实际执行。

正常运行

当然 有人会好奇 .exe是根据什么目录来寻找.dll的

当 .exe 运行时，操作系统会按一个特定的顺序去查找并加载它所需要的 .dll 文件（被导入库标记的.dll），这个顺序就是 DLL 搜索顺序 (Dynamic-Link Library Search Order)。如果找不到，程序就会报错（例如 找不到xxx.dll）并无法启动。其中.exe 所在目录是最高优先级的.dll搜索位置

动态链接的优点

1内存占用（运行时）

动态链接库（.dll）：包含实际的函数实现、全局变量、资源等。

导入库（.lib，对应 DLL）：只包含符号导入信息（函数/变量的名称、序号、重定位信息），不包含实现代码。

静态库（.lib，对应静态链接）：包含完整的函数实现代码（类似多个 .obj 的打包）。

所以：使用 DLL 时，.lib 很小。使用静态链接时，.lib 很大。

DLL：多个进程可以共享同一份只读代码段（物理内存中一份），数据段各自独立。

节省物理内存（尤其是代码量大的库）。

静态库：每个 exe 独立拷贝一份实现代码到自己的进程地址空间。

内存占用随进程数线性增长。

2更新部署（不发整个 exe）

DLL 更新

前提：API 接口不变（函数名、参数、返回值、调用约定、数据结构布局不变）。

行为：只需替换 DLL 文件，所有调用它的 exe 无需重新编译、重新链接，直接获得新实现。

例外：若接口变更，exe 必须重新编译。

静态库更新

即使只修改内部实现（接口未变），也必须：

运行时库

运行时库（Runtime Library）

运行时库是与编程语言的执行环境（Runtime Executor）相绑定的基础代码集合，其职责是为该语言编写的程序提供内存管理、异常处理、程序启动与终止等底层支撑。它与普通软件开发工具包（SDK）库在物理形式上并无区别——均以静态库（.lib）或导入库配合动态库（.dll）的形式存在，链接机理也完全相同。二者的根本差异在于职责定位：运行时库构建程序的执行地基，SDK库提供操作系统或第三方平台的功能扩展（如网络通信、图形渲染、文件访问等）。

运行时库的部署位置取决于运行器本身的归属：

当运行器即为操作系统本身时（如C/C++语言），运行时库已被预先置于编译器的默认库搜索路径中，并直接列入其默认链接列表。因此，开发者无需手动配置路径或导入库，链接过程即可自动完成。在此场景下，运行时库表现为操作系统平台SDK的一个子集，这即是”运行时库是被内置到编译器默认环境中的SDK库”这一常见说法的来源。

当运行器需要独立安装时（如Java虚拟机的JRE、Python解释器），运行时库则被部署于该运行器的安装目录下，并不进入操作系统目录。此时运行时库与操作系统平台SDK呈并行关系，二者相互独立，各自承载不同层级的职责。

综上，运行时库与普通SDK库的本质区别在于职责——地基与功能的区分——而非是否默认内置；默认内置仅是运行器为操作系统时的特例现象，并非运行时库的普遍定义。
