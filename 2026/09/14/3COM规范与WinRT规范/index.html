COM规范：跨语言调用的二进制标准

COM 组件的承载形式只能是动态链接库（DLL），不能是静态链接库（.lib）。

下面我们先讨论COM机制后讨论承载限制的原因

高级语言调用传统C/C++ 动态链接库的困境

绝大多数SDK的底层核心基于C/C++开发。高级语言（如C#、VB、Python、Java）由于自身运行环境（虚拟机/解释器）的限制，难以在不借助原生代码的情况下实现同等性能或系统级访问的SDK核心功能，因此必须复用现存的、高效的C/C++ SDK

然而，当高级语言试图间接调用这些C/C++ SDK时，会遇到一系列根本性障碍：

障碍的根源在于：传统C/C++动态链接库的整个交互体系是专为C/C++语言设计的。

头文件（.h）是C/C++专属的 头文件中的类型定义、函数声明、预处理宏（#define）、类定义等，都遵循C/C++的语法和语义规则。其他语言（如C#、VB、Python）没有预处理器的概念，也无法直接理解typedef、class、虚函数表等C/C++特有的语言构造。

导入库（.lib）和动态库（.dll）的导出机制是配合头文件（.h）工作的 .lib文件中记录的函数符号、参数压栈顺序、调用约定（__cdecl/__stdcall等），以及C++类导出时依赖的虚函数表布局，都是按C/C++编译器的特定标准来设计的。不同编译器甚至同一编译器的不同版本，这些二进制约定都可能不兼容。

这些根源性问题，导致高级语言在调用C/C++ SDK时，必然面临以下跨语言交互难题：

内存管理责任不明：C/C++侧手动分配的内存在何时、由谁释放？高级语言的GC无法感知原生内存，容易导致泄漏或重复释放。

类型系统不兼容：C/C++的指针、引用、结构体对齐、联合体、回调函数指针等类型，在高级语言中缺乏直接对应物，需要复杂且易错的映射。

接口版本难以演化：C/C++接口的任何变更（如增加函数参数、调整类成员顺序）都会破坏二进制兼容性，导致所有旧客户端崩溃，而头文件的重新分发和同步更新极其困难。

结果：如果微软只提供 C/C++ 的头文件和库，那么只有 C/C++ 能轻松调用。其他语言要么用不了，要么需要额外写封装层——这相当于为每种语言重新实现一遍接口逻辑。

二、COM 的解决方案

COM 定义了一套语言无关的二进制标准 包含两个部分：

二（1） COM 组件（本体，.dll）

**COM组件的二进制接口是“自描述”的,二进制接口（不是指 API 接口，而是 DLL 内部供外部对接的实现部分——即导出表的等价物），其“自描述”是指：COM 组件在导出表（函数名→地址）的基础上，额外携带了类型信息（方法名、参数类型、返回值、调用约定等），让调用者能在运行时通过 IUnknown::QueryInterface或 IDispatch::GetTypeInfo  **发现组件支持哪些接口和函数,从而不用写API接口声明文件了,减少了调用难度(C/C++除外,因为它们不但没省略API接口声明文件,还要写配合COM规范写一份更复杂的.h)。

这意味着：微软只需要维护一份 COM 组件的二进制代码，除了C/C++语言都能直接用简单的方式调用它，这样就大大减少了微软为每种语言单独编写 API 声明文件和调用规范的工作量。

VBScript（完全支持）

JavaScript（仅在 Windows Script Host 中；IE 环境受限且已停止维护）

PowerShell（使用 -ComObject 参数）

Python（使用 win32com.client）

而对于 C/C++，COM规范 反而让接口声明变得更加复杂。

传统方式：头文件只需要描述函数的参数和返回值，简洁直接。

之所以要写成纯虚类，是为了配合 COM 的运行时机制（利用 DLL 内部的自描述信息），在调用过程中完成对纯虚类的实际“填充”——也就是让纯虚类真正“落地”为可调用的对象方法。

结果是：头文件不仅没有简化，反而比传统 C/C++ 更臃肿、更难以手写，这是为了支持SDK跨语言调用做出的C/C++方的牺牲。

二（2）配套的导入库（适配层，.lib）

这个 .lib 不是传统导入库，而是专为 COM规范设计的导入库。但是COM 导入库和传统导入库在工作原理上是一模一样的,都是基于根据导入描述符生成的导入表来在运行时加载.dll。

三、C++ 调用 COM 确实更麻烦，这是故意的取舍

为什么微软不给 C++ 也弄个简单封装？因为 C++ 是系统级语言，COM 本身就是为 C++ 设计的底层接口。其他语言（C#、VB）对 COM 的友好封装，是建立在 .NET CLR 这个“大管家”之上的。如果微软给 C++ 也做一套类似的封装，那这套封装本身也会增加复杂性和编译依赖。

后来微软确实做了这事：C++/WinRT 就是那个“为 C++ 提供的现代化封装”。它用工具 (cppwinrt.exe) 读取 .winmd 元数据，动态生成 C++ 头文件，然后用标准 C++ 类包装底层的 COM 调用，让 C++ 开发者也能像 C# 一样自然地调用 WinRT 组件。代价是需要额外的工具链和项目配置。

为什么COM组件的承载不能是LIB

COM 组件以 DLL 为载体（没有静态库形式），配套的 .lib 文件是一种专为 COM 设计的导入库，用于在运行时（通过 CoCreateInstance 等机制）动态连接该 DLL。那么，为什么不能像写静态库那样，把 COM 组件直接写进 .lib 文件呢？

根本原因在于：其他编程语言的运行环境本身就没有“链接静态库”这个阶段。

静态库 (.lib**)** 是 C/C++ 编译器/链接器专用的产物。它里面包含的函数名修饰、二进制代码布局等，都严重依赖于特定的 C++ 编译器和链接器实现。

像 C#、VB、Python 等其他语言的运行时（如 .NET CLR、Python 解释器）并不包含一个能理解 C++ 静态库格式的“链接器”。它们无法直接解析和调用 .lib 文件中的代码。

因此，为了让 COM 组件能被任何语言调用（即实现跨语言能力），它必须采用 DLL 这种支持动态链接的形式，成为所有语言都能“够得着”的独立二进制模块。

如果强行把 COM 组件实现为静态库 (.lib)，那就意味着它只能服务于 C/C++ 语言，而且使用起来会比现有的 COM 机制更麻烦（因为静态库无法支持运行时发现组件、无法实现接口与实现的分离等核心 COM 特性），所以这种做法既不可行，也无人采用。

COM规范SDK在CPP项目中的调用

// 假设你还涉及调用了某个返回字符串的方法

WCHAR* pStr = NULL;

pSomeInterface->GetString(&pStr);// … 使用 pStr …

基于我们刚刚提到的 COM 组件内二进制接口的自描述能力，C/C++ 的调用机制是这样的：

我们在 .h 文件中声明一个纯虚类（API接口），其中写满了要调用的虚函数。这个纯虚类只是一个编译时的“占位符”，告诉编译器对象“长什么样”。

在运行时，我们调用 CoCreateInstance 命令。这个命令会进入 COM 组件（DLL）内部，读取它已经自描述好的二进制接口信息（虚函数表布局、方法地址等）。

CoCreateInstance 根据读取到的信息，创建一个子类对象。这个子类对象内部根据二进制接口信息重写（填充） 了我们在 .h** 里定义的那个纯虚类里的所有虚函数，让每个虚函数都指向 DLL 中真正的函数实现地址。**

最后，CoCreateInstance 将这个创建好的对象的地址返回，并由一个**COM规范下的”智能指针”(实际上是个类 我们称其为智能指针(类))**CComPtr管理(管理是指把地址传给了智能指针类中的一个指针变量进行储存)。我们通过这个”智能指针”(内的指针变量)解引用，并以访问类成员的方式（pInterface->Method()），就可以直接调用 DLL 内部那个真正实现该方法的对象了。

COM 环境与 COM 资源的承载关系

核心模型：

COM 资源（COM 对象） 比作 “人”

COM 环境（COM 初始化后的运行时状态） 比作 “房子”

生命周期映射：

CoInitialize(NULL) → 建房 创建 COM 环境，相当于为后续的资源提供容身之所。

调用 COM 接口、创建和使用 COM 对象 → 住人 资源（COM 对象）在环境中被创建、使用，依赖于环境的支撑。

CoUninitialize() → 拆房 销毁 COM 环境。该环境中所有尚未释放的 COM 对象，都会被强制释放（相当于“强制杀死”）

关键约束机制：未及时撤离的资源会死亡

若在 CoUninitialize 前未手动释放某个 COM 对象，环境销毁时它会被强制释放，外部指针变为悬空。

任何后续通过该指针访问对象的行为，都将导致未定义行为（通常为访问违例/崩溃）。

这就会导致下面这两个问题：

1无法跨 COM 环境保留资源

资源（对象）与其创建时的 COM 环境强绑定。

环境销毁后，即使重新 CoInitialize 建立新环境，也无法将旧环境中的对象迁移过来继续使用。

跨 COM 环境使用对象是被禁止的，技术上不可行，逻辑上也不安全。

2必须在销毁环境前完成所有资源释放

程序员必须在其代码中，于 CoUninitialize 之前，对当前环境中所有不再需要的 COM 对象主动调用 Release。

由于无法跨环境复用资源，应将生命周期相关联的所有资源集中在同一个 COM 环境中管理，避免反复卸载重建环境。

智能指针的存在意义

限制：重写对象大 + 必须在堆上显式管理声明周期

方案一

深拷贝→ 内存和时间开销爆炸→放弃深拷贝 （平常我们因为对象小,拷贝一份的内存开销不大,就直接选择了这个方案）

方案二

进行传堆区地址进行共享→ 双重释放问题→ 需要一种机制来协调释放（谁释放、什么时候释放）→ 引用计数机制(Release()和AddRef())→ 手动维护引用计数容易出错→ 智能指针自动管理

COM规范下的智能指针(类)CComPtr的功能实现

在之前的讨论中，我们提到 CComPtr 这类COM智能指针实现了两个核心功能：与接口类型的强绑定——即智能指针在类型层面与具体的COM接口（如 IXxx）绑定，确保类型安全。

智能化的资源管理——其核心在于：类内部持有一个原始接口指针，但在发生浅拷贝时，能够通过引用计数机制避免双重释放（double free） 问题。

接下来，我们将从这两个功能入手，分别探讨 CComPtr 的实现原理。

};

COM 智能指针本质上是一个类模板。 这个类的对象中只包含一个指针成员。 指针成员的类型，就是通过模板参数指定的 API 接口类型（例如 ISpVoice*）。

当这个智能指针对象被创建时，指针成员是空的（nullptr）。

之后，CoCreateInstance 会完成以下工作：

在堆上创建一个真正的 COM 对象（称为“重写对象”），该对象实现了 API 接口中声明的所有虚函数（包括 AddRef 和 Release）。

将这个对象的接口指针，写入智能指针对象内部的指针成员,让其值从nullptr（不指向任何有效对象）变为重写对象地址,从而指向重写对象内存的情况。

重写对象地址是如何传递给智能指针类的指针成员的？

智能指针类重载了 operator&。

当你对智能指针对象取地址（&obj）时，重载后的 operator& 返回的不是智能指针对象本身的地址，而是返回其内部指针成员 p 的地址（即 &p）。

CoCreateInstance 的参数中要求传入 &obj：

实际拿到的是 &p

它是一个二级指针（类型为 T**）即指针p的所在地址

通过这个二级指针，CoCreateInstance 可以直接修改智能指针对象内部的 p 的值，把它改为新创建的重写对象的地址。

智能指针的“智能”体现在哪？

智能指针对内部的指针成员 p 提供了自动生命周期管理：

在构造、拷贝构造、赋值中自动调用 AddRef

在析构、赋值覆盖中自动调用 Release

这一点和普通类里手写指针管理类似，但不同的是：

它没有使用深拷贝，而是通过引用计数 + 自动调用 AddRef/Release 的方式，避免了双重释放问题。

这确实是它的核心特征，也是它被称为“智能指针”的原因。 （从实现角度看，逻辑并不复杂。）

智能指针的指针指向重写对象的关系

智能指针对象的指针成员 p 指向的是重写对象（即 CoCreateInstance 创建的那个 COM 对象）。

这个重写对象中：

重写了 API 接口类中的纯虚函数 AddRef 和 Release。 而且这两个纯虚函数是从 IUnknown 继承而来的声明。

那为什么 API 接口类不自己写 AddRef 和 Release 的纯虚函数？

因为所有 API 接口类都需要 AddRef / Release 的声明（才能被智能指针调用）， 但没必要每个接口都重复写一遍“纯虚函数声明”,不然太麻烦。

实际做法是：

声明来源：IUnknown 已经定义了 AddRef / Release 为纯虚函数 → API 接口类（如 ISpVoice）只需继承 IUnknown，就自动拥有了这两个纯虚函数的声明,然后实现重写。

AddRef / Release 如何避免双重释放？

API 接口类在继承 AddRef / Release 的同时，也继承了一个 ULONG** 类型的引用计数变量**（通常叫 m_cRef 或 m_dwRef）。

每次 AddRef 被调用（例如智能指针拷贝时），引用计数 +1

每次 Release 被调用（例如智能指针析构时），引用计数 −1

如果 Release 发现引用计数 减1后等于 0，它就会执行 delete this，销毁重写对象

这样，只有最后一个持有该对象的智能指针析构时，对象才会被真正销毁。 不会出现多个指针释放同一块内存的情况（双重释放），也不会出现对象始终不被释放的问题（内存泄漏）。

CoCreateInstance的浅封装形式(1.辅助函数 2.父、子对象)

在 COM 规范下，CoCreateInstance 的浅封装体现在两个层次：

一、全局辅助函数

对于一个 SDK 的 .h 文件中的所有 API 接口而言，通常有一个统一的全局辅助函数（如 SAPI 中的 SpEnumTokens）作为入口。不同的 SDK，其辅助函数也不同。这个全局辅助函数的作用是：浅封装 CoCreateInstance，创建顶层 COM 对象（父对象），并填充其虚函数表。

二、接口方法作为“类辅助函数”

当顶层对象被创建后，我们可以通过它的某些接口方法（如 Item、OpenKey）来创建子对象。这些接口方法在功能上类似于“辅助函数”，但它们不是全局的，而是隶属于某个接口。它们的作用是：填充另一个类的虚函数表，生成子对象，并将子对象的地址通过输出参数返回。//这里的返回值是子对象的地址

三、父子关联的建立

这种设计的关键在于：子对象是通过父对象的方法创建的，因此子对象天然知道自己的父对象（或至少知道自己的上下文）。父对象通过输出参数获取子对象的地址，从而建立起父子之间的连接关系。

四、为什么子对象不应该用全局辅助函数创建？

虽然技术上子对象也可以用全局辅助函数直接创建并生成对象，但这样做会导致子对象失去与父对象的联系。没有这种联系，子对象就无法知道自己属于哪个父对象、处于什么上下文中，后续的功能调用可能出错或无意义。因此，COM 规范下的典型设计是：顶层对象由全局辅助函数创建，子对象由父对象的方法创建，以确保对象之间的关联关系完整。

接下来我们举一个COM规范下的SAPI的SDK调用

WinRT规范

WinRT 是建立在 COM 之上的一层现代化规范

它最主要是解决这个问题：COM规范下的C++调用太过于复杂

下面我们对比 WinRT 与 COM 在调用层面的差异，并进一步说明 C++ 如何调用 WinRT 规范下的 SDK。

COM与WinRT 在不同语言下的体验差异

1、COM 的代价（分层视角）

COM 规范以 C++ 抽象类 + 虚表 + 引用计数 + HRESULT 作为二进制接口标准。 这套设计换取了极佳的跨语言能力，但代价不是均匀分摊的：

C++ 调用 COM 时： 开发者必须手动调用 AddRef / Release 管理生命周期、通过虚表访问方法、检查每个 HRESULT 返回值。 类型系统不提供任何自动化支持 —— 调用模式非常复杂。

C# / VB / Python 等其他语言调用同一 COM 组件时： 开发环境通过读取类型库（Type Library）或元数据，自动生成代理/封装代码。 引用计数、HRESULT 检查、对象创建等底层细节完全被语言投影隐藏。 开发者只需像使用普通对象一样 new、调用方法、由 GC 管理内存 —— 完全不复杂。

结论：COM 把复杂性压在了 C++ 这一侧，对其他语言几乎是透明的。

2、WinRT 对 C++ 的改进

WinRT 在 COM 基础上引入了元数据（.winmd）和代码生成器。

传统 COM 下 C++ 的处境： 头文件里全是抽象类声明，开发者必须手动完成虚表调用、引用计数、HRESULT 检查。

WinRT 的改进方式： 对于 C++，生成器（如 cppwinrt.exe）会生成一个投影层 .h 文件。 这个 .h 把底层的 COM 抽象类包装成更自然的 C++ 类型和调用方式（如异常代替 HRESULT、RAII 管理生命周期）。

结果： C++ 开发者使用新的 .h 后，调用体验从“复杂”变为“简单”。 但生成器的存在感仍然明显——需要显式配置和调用。

结论：WinRT 专为 C++ 解决了 COM 的历史痛点，但 C++ 开发者仍能感知到生成器的存在。

3、WinRT 对其他语言（C# 等）的影响

对其他语言而言，WinRT 和 COM 在用法上几乎没有区别：

语言投影（如 C# 的 cswinrt.exe）自动读取 .winmd 元数据，生成封装代码。

生成器被完全集成到编译工具链（如 MSBuild）中，对开发者完全透明。

开发者只需添加项目引用，然后直接 new、调用方法，体验和调用普通 COM 组件一样简单。

结论：WinRT 并没有给非 C++ 语言带来任何额外负担，生成器的存在感极低。

那么，什么是公寓？什么是同步方法和异步方法？.get()** 又是什么？**

公寓我们先不展开，这里先简单交代其中的同步方法和异步方法。

同步方法是调用后要等它执行完才能返回的方法。你调用它，线程会停在那里，等它执行完，拿到结果，再继续往下走。

异步方法是调用后立即返回一个“代表未来结果的对象”的方法。你调用它，它不会让你等，而是马上给你一个对象，代表“这个操作以后会完成”。WinRT 里异步方法的名字一般以 Async 结尾，比如 SynthesizeSsmlToStreamAsync、ReadAsync。

下面我们就详细讲讲，公寓和线程模式之间到底是什么关系。

任何 C++ 程序，只要它开始执行，就至少有一个线程——通常叫主线程。 main() 里的代码就是在这个主线程上顺序执行的。所以：

这就是一个单线程程序。它占一个线程，这个线程从头到尾顺序执行。

那公寓和线程是什么关系？公寓首先是建立在“线程”这个概念之上的：你调用 CoInitializeEx 或 winrt::init_apartment 之后，当前线程就被登记进了一个公寓。所以公寓和线程是绑定的。

但公寓不只是“一个线程”这么简单。它比线程多了三样东西：一个归属标记、一套存储结构、一套调用规则。下面我们逐个说。

  • 归属标记。 每个线程在调用 CoInitializeEx 或 winrt::init_apartment 之后，就被打上了一个标记：这个线程属于 STA 公寓，或者这个线程属于 MTA 公寓。

这个标记决定了这个线程之后能怎么用、能碰哪些东西。这里要特别点明一句：COM 的 CoInitialize(NULL) 这个 COM 组件初始化，就包含了把该线程放到 STA 公寓这一步，只不过我们当时没有提名。

这里说明一下：任何进程当中的线程有且只有这两种公寓归属。即便项目不涉及 COM 规范，作为运行时的 COM 运行时仍然会在每个程序运行时建立隐式 MTA，没有显式初始化的线程默认被视为隐式 MTA 的成员，COM 运行时会一直存在。并且MTA公寓在一个进程当中有且仅有一个。

第二，存储结构。 这个标记存在哪里？不存在你的代码里，而是存在 COM 运行时自己管理的一套内部数据结构里。COM 运行时是一个运行时库 DLL，它在内部记录了“哪些线程属于哪个公寓”“哪个公寓里有哪些线程”这些信息。你不需要知道它具体长什么样，你只需要知道：调用 init_apartment 之后，当前线程就被登记进了这套内部结构。

第三，调用规则。 标记只是身份，真正重要的是它对应的调用规则：

“调用者线程”指的是执行那行调用代码的线程。 第四行 STA 列下“必须在一个公寓”的意思是：调用者线程必须和被调用的东西在同一个 STA。 对 STA 来说，一个公寓里只能有一个线程，所以“在同一个公寓”就等价于“只能是那一个线程”。 当然，违反这条规则也不会直接崩溃，这里会触发我们后面要讲的封送机制。

先讲主线程是 STA 的情况

首先，如果开的副线程不做任何初始化，它会被默认视为隐式 MTA 成员。 当它去调用 STA 对象时，属于跨公寓调用，会触发封送。

但是，如果强制把副线程开成 STA，那么根据 STA 的规则——一个 STA 里只能有一个线程——COM 只能给这个副线程新建一个 STA，而不能让它加入主线程所在的 STA。 这时候，虽然主线程和副线程都属于 STA，但它们不是同一个公寓，互相调用仍然属于跨公寓调用，仍然会触发封送。

再看 MTA 列

MTA 列下的情况就简单了： 我们的调用者线程开一个异步函数，这个异步函数的工作线程来自线程池，而线程池线程默认被视为属于隐式 MTA。 这个隐式 MTA，也是整个进程唯一的 MTA 公寓。 调用者线程和异步函数线程同属于一个 MTA 公寓的不同线程，没有打破 MTA 的规则——一个 MTA 里可以有多个线程。 而如果我们新建的是 STA 线程，就会触发封送。

那这个隐式 MTA 是从哪来的？

进程启动时，Windows 进程会自动创建一个隐式的 MTA。这是最早、最默认的 MTA。 也就是说，你的进程刚起来，还没有任何线程调用 CoInitializeEx，但 COM 运行时已经替你准备好了一个 MTA，这个 MTA 被称为隐式 MTA。

它的特点是：

进程里任何没有显式加入公寓的线程，默认都被视为属于这个隐式 MTA；

这个 MTA 是进程级别的，不是线程级别的；

它一直存在，直到进程结束。

所以你可以理解为：每个 Windows 进程天生就有一个 MTA。 这个 MTA 就是为了接住意外情况的，是进程级别、所有线程的兜底。 线程池里的线程默认就属于这个隐式 MTA，但隐式 MTA 本身不是线程池。

还要注意：隐式 MTA 和显式 MTA 是同一个公寓，进程里只有一个 MTA。 后来线程调用 CoInitializeEx(MTA) 或 init_apartment() 时，加入的就是这个 MTA，不会新建第二个 MTA。

同一公寓的规则是 COM 运行时强制执行的。 你违反规则，COM 不会直接崩，但它会给你做封送——把调用打包，排队到目标公寓的线程上执行。也就是第二行的跨公寓调用对象。

为什么需要公寓

因为 COM 对象不是线程安全的。 微软不想让每个 COM 组件作者都自己写锁，于是设计了公寓模型：

如果你把对象放在 STA，COM 保证只有那个线程能直接碰它，其他线程的调用会被排队进来。

如果你把对象放在 MTA，COM 保证多个线程可以并发调用，但对象作者要自己保证线程安全。

这样，组件作者和调用者都有明确的规则可循。

这里我们回到同步方法和异步方法的详细介绍。

同步方法是调用后要等它执行完才能返回的方法。你调用它，线程会停在那里，等它执行完，拿到结果，再继续往下走。

异步方法是调用后立即返回一个“代表未来结果的对象”的方法。你调用它，它不会让你等，而是马上给你一个对象，代表“这个操作以后会完成”。你可以稍后去取结果，也可以边等边干别的。WinRT 里异步方法的名字一般以 Async 结尾，比如 SynthesizeSsmlToStreamAsync、ReadAsync。

.get() 是 C++/WinRT 提供给异步操作对象的一个方法。它的作用是：在当前线程上死等异步操作完成，然后取回结果。它把“等待异步结果”这个动作变成了同步等待，异步任务本身仍然是异步执行的。

假如我们的一个函数是异步的，因为它的异步是封装好的，我们没办法强制它顺序执行。但是我们有时候就是会遇到想要顺序执行的情况，所以加上 .get() 之后，不论这个异步函数是跑在隐式 MTA 上还是 STA 上，我们都可以让当前线程阻塞等待，等它完成之后，当前线程才继续下一步。

需要说明的是，.get() 做的事是在当前线程上阻塞，等异步操作完成，然后取回结果。它并不会把异步任务和当前线程关联，异步任务本身仍然在它原来的地方执行（通常是隐式 MTA），没有被搬到当前线程。.get() 只是让当前线程停下来等，等到了就继续走。

但在 STA 线程上用 .get() 有风险：如果异步操作完成后需要回调回 STA，而 STA 又被 .get() 阻塞了，就会死锁。所以微软推荐在 STA 上用 co_await，不要用 .get()。

因为.get() 就是让当前线程阻塞，死等异步操作完成。co_await 则是挂起函数，把线程让出去，但不阻塞线程。让出去的 STA 线程继续跑消息泵，所以如果副线程需要回调回这个 STA，回调能排进消息队列并被处理。副线程顺利完成，结果传回，主线程的协程被恢复，继续往下走。所以 co_await 不会像 .get() 那样因为阻塞 STA 线程而导致死锁。而这种让原工作挂起、让出线程的行为，就是协程。
