4T02 并发的底层支持

发表于2026-09-20|更新于2026-09-22
|浏览量:

在上一期节目中，我们讨论了并发。本系列的后续内容将转向更接近操作系统的底层概念，例如 CPU 调度、线程、分页和虚拟内存。

这些主题的难点在于，它们都和我们尚未详细讲解的概念密切相关。今天，我们将深入探讨进程的技术细节。

分配给进程的内存有一个专门的名称，叫做进程的地址空间，它对应我们此前在 《if 和 while 底层物理实现》中介绍过的内存四区。关于这一概念，稍后还会展开讨论，这里先作保留。

然而，一个进程不仅仅是它的地址空间。现代操作系统使用并发，通过交替访问计算机资源，允许多个进程执行。而并发意味着多个进程需要交替使用 CPU，因此每个进程除了地址空间之外，还需要保存自己的 CPU 状态、寄存器、程序计数器等运行时信息。

这些运行时信息保存在内核空间中。内核空间在虚拟地址布局中通常位于用户空间上方。为了区分，我们通常把进程的地址空间称为用户空间。

需要补充的是，每个进程在自己的虚拟地址布局中都会看到内核空间，但这并不意味着每个进程都独享一份如此大的内核内存。以 32 位 Windows 的典型布局为例，每个进程的虚拟地址空间为 4GB，其中内核空间占 1GB，用户空间占 3GB。内核空间虽然出现在每个进程的页表里，但所有进程共享同一份内核映射。内核代码、内核数据、每个进程的 PCB、内核栈以及调度队列等，都位于这块共享的内核空间中。进程信息集中存放于内核空间，操作系统便能更方便地协调各进程，CPU 访问的交替也因此可以依赖内核空间实现。

在内部，CPU 访问的交替是通过将进程放入内核空间中的调度队列来实现的。到本文结束时，你会理解这一机制的具体工作方式。在此之前，我们先简要介绍一个基础概念。例程（routine）通常指一段完成特定功能、可被反复调用的代码，也就是通常所说的函数、方法或过程。用户自己编写的函数，例如一个接收两个向量并输出叉乘结果的函数，属于用户内存中的例程；而负责协调所有进程、实现 CPU 访问交替的切换例程，则属于内核例程。

现在关键的一点是：在任意给定的时刻，只有单个进程可以使用 CPU，而所有其他进程都在等待轮到自己。这具体是如何在内核内存中实现的呢？

要理解这一点，需要先回到 CPU 本身。请记住，CPU 内部通常包括通用寄存器、指令寄存器、地址寄存器、栈指针，甚至标志位等组件。当一个进程获得 CPU 访问权限时，它会利用这些组件来操作和移动数据。这本质上就是运行程序的过程，我们已在之前的系列《从 0 开始的计算机架构》中介绍过。

但问题也正出在这里。CPU 内部只有一套寄存器，而进程却有很多个。在多个进程之间交替使用 CPU，并不像听起来那么简单。如果我们直接切换进程，获得访问权限的进程将处于属于前一个进程的 CPU 状态中。这会导致两个问题。

首先，这存在严重的安全风险，因为当前进程可以访问前一个进程的敏感信息。试想，前一个进程正在处理密码哈希时，部分密码可能还储存在寄存器当中，没有任何机制可以阻止当前进程为了恶意目的读取该信息。因此，第一个关注点是安全性。

现在，我们假设所有进程都是诚实的，不会利用前一个进程留下的信息，这是否就解决了问题？没有。即使当前进程无意使用这些信息，它仍然需要操作寄存器来执行自己的任务，这样一来就会改变前一个进程的 CPU 状态。因此，当之前的进程稍后再次获得 CPU 访问权限时，它被中断的 CPU 状态将会丢失。因此，第二个关键点就是执行的正确性。

让我用一个具体的例子来说明：

假设我们想运行两个程序。为了便于观察，我们先用反汇编器把它们转换成汇编代码。这里稍微提一句，什么是汇编和反汇编：

汇编，是把人类可读的汇编助记符翻译成机器可执行的机器码，是“从高到低”的翻译过程。

反汇编，是把机器码还原成汇编助记符，是“从低到高”的逆向翻译过程。但由于符号信息和代码/数据边界在编译后已经丢失，反汇编的结果通常不唯一、也不完整。

要由计算机运行，代码最终必须编译成机器码，但二进制代码难以理解，为了直观，我们以汇编语言展示这些指令。

假设这两个程序同时启动。为了运行它们，它们会被加载到内存中。为简化起见，我们先假设操作系统使用的并发模型允许每个进程最多执行两条指令，然后切换到另一个进程使用 CPU。

为了开始执行第一个进程，操作系统设置程序计数器，使 CPU 可以开始为该进程获取指令。第一条指令告诉 CPU 将地址 12 中的值加载到寄存器 0 中。第二条指令告诉 CPU 将数值 20 加载到寄存器 1 中。至此，两条指令已经执行完成。

此时，操作系统会设置程序计数器，使 CPU 开始执行第二个进程。现在程序计数器指向第二个进程的可执行代码，我们可以说，CPU 已被分配给该进程。

请注意，尽管第二个进程现在控制了 CPU，但第一个进程之前使用的数据仍然保留在寄存器中。再次强调，我们假设第二个进程并非恶意，会安分守己地处理自己的任务。第二个进程的第一条指令告诉 CPU 将数值 100 加载到寄存器 0 中。下一条指令告诉 CPU 把 35 放到寄存器 1 中。现在两条指令已经执行完成，因此操作系统必须将 CPU 重新分配回第一个进程。为此，需要将程序计数器设置为正确的地址，使第一个进程能从它中断的地方继续执行。但这里出现了第一个错误：

我们在将 CPU 分配给第二个进程之前，并没有将程序计数器的值保存在任何地方，因此无法恢复第一个进程。

我们假设操作系统已经保存了程序计数器的值，并且能够正确恢复它。第一个进程重新获得控制权，并从中断的地方继续执行。第三条指令告诉 CPU 将寄存器 0 和寄存器 1 当前保存的值相加，并把结果保存在寄存器 0 中。这两个值原本应该分别是 12 和 20，然而由于第二个进程在执行期间修改了两个寄存器的值，CPU 现在利用错误的值相加。CPU 按指令执行，无法知道出现了什么意外情况，因此它继续使用错误的数据执行此进程。

这个问题在这个示例中持续存在，最终我们会把两个进程的结果都搞乱。更糟糕的是，这些错误结果可能还是不确定的：例如，如果我们添加了第三个进程，或者第二个进程晚几毫秒启动，我们看到的错误结果也会完全不同。当我们考虑到现代计算机系统同时处理几百个进程时，这个问题将会十分棘手。更糟糕的是，实际上很难预测进程执行的确切顺序，我们将会在 CPU 调度视频中学习这一点。

为了确保安全性，并在执行多个进程时避免冲突，切换 CPU 访问权限时需要额外的步骤。 让我们沿用同样的例子：两个进程同时运行，我们仍然允许每个进程最多执行两条指令，然后中断它并切换到另一个进程。

但是，切换时操作系统不会简单地覆盖地址寄存器，让 CPU 跳转到第二个进程的可执行代码。相反，它会首先运行一个特殊例程，用于捕获 CPU 的当前状态，并将其保存到一个数据结构中，也就是进程控制块（PCB）。这样做的目的是将寄存器、标志位和程序计数器的内容复制到内存中，以便当该进程重新获得 CPU 控制权时，可以恢复它被中断时的状态。操作系统会为计算机上运行的每一个进程保存一份 CPU 状态的副本。

在中断进程的 CPU 状态被捕获并安全保存之后，操作系统立即恢复下一个进程的 CPU 状态。如果该进程此前从未运行过，那么它的状态中除了程序计数器之外全是 0，于是 CPU 会从该进程的第一条指令开始执行。

这些额外的步骤解决了两个问题： 第一，一个进程再也无法访问前一个进程正在使用的信息；第二，由于它自身的状态没有被其他进程修改，它可以继续执行，并且确信自己使用的数据是正确的。

这种捕获上一个进程的 CPU 状态，并恢复另一个进程的状态以使其继续执行的操作，是上下文切换中的核心操作之一。上下文，指的就是进程继续执行所需要的所有现场信息。这是操作系统在多个进程之间共享 CPU 时，保证安全性和正确性的关键机制。不过，上下文切换并不只是简单地保存和恢复 CPU 状态，下面我们讲解上下文切换所依赖的所有现场信息是什么。

前面我们提到过，进程包含地址空间，但不包含内核空间的内存。程序计数器和指令寄存器等，可以非正式地定义为该进程的 CPU 状态，它们也属于进程的一部分。但除这两项之外，一个进程还包含什么？

一个进程还需要一组打开的文件，以及分配给它的输入输出设备。 这是可视化一个进程最简单的方式。所以如你所见，进程不是一个单一的实体，而是与其他进程完全隔离的上下文。

也就是说，进程不只是单一的代码。地址空间、CPU 状态、打开的文件和输入输出设备，这四类信息共同用于还原现场：代码和 CPU 信息用于让指令流正常运行，交互设备和文件的打开状态则让进程的访问对象（内存、文件或设备）保持正确。

内核中利用这四项信息保存当前进程上下文、恢复下一进程上下文，从而完成进程切换的程序，就是切换例程。切换例程所执行的操作，称为上下文切换。当我们切换进程时，实际上就是在替换系统运行的整个上下文。这就是进程切换的基本原理。

这也从高层解释了，为什么多个进程可以拥有相同的可执行指令，但在执行时却会产生不同的结果。因为问题不仅在于进程本身，还在于执行这些指令的上下文。

因此，描述一个进程的最佳方式是：在被切换的视角下，进程就是一个上下文。

现在有一个问题：如果一个进程是这样一个完整上下文，从寄存器等底层组件，到文件列表等高层内容，我们如何将它放入队列中？ 也就是说，进程在切换视角下是一个上下文，它不像一个对象那样可以直接用作数据结构中的一个元素。我们要如何管理它？

答案是PCB，也就是进程控制块。 这是操作系统用来跟踪每一个进程的特殊数据结构。由于每个进程都是唯一的，在 PCB 中，我们为每个进程给定唯一的进程标识符 PID。

一个进程还拥有运行状态，可能是 New、Running、Ready、Waiting、Terminated 当中的任意一种，我们将会在后面详细讨论它。此外，一个进程还拥有程序计数器、一组通用寄存器、指令寄存器和标志位。根据硬件不同，一个进程可能还有堆栈指针、索引寄存器、累加器等其他组件，在此处不再一一列出。通常，这些可以非正式地称为进程的 CPU 状态，除去运行状态和 PID。

你还记得上下文切换需要捕获每个进程的 CPU 状态吗？这正是存储这些数据的位置，在这个ProcessControlBlock特殊数据结构中。

关于内存，操作系统还必须跟踪分配给每个进程的所有内存块。还记得每个进程都有自己的地址空间吗？实际上，并发运行多个程序会带来新的安全问题。因为如果没有额外的防护措施，任何进程都可以写入另一个进程的地址空间。操作系统必须了解这些边界，以便拦截任何恶意的内存访问。此外，当创建一个新进程时，操作系统需要了解每个现有进程的地址空间，以正确地为新进程分配可用的内存区域。

因此，进程控制块应包含内存管理信息，至少包含每个进程地址空间的内存限制。

在这里，我们还可以添加分配给该进程的其他资源，例如 IO 设备列表或打开的文件，来填充这个数据结构。当然，你现在看到的这个结构只是一个示例。

如果你想要查看真实的表现，可以查看 Linux 内核源代码的相应路径。值得注意的是，我们的示例结构 PCB，在代码中被称为任务结构体（task_struct），而不是进程结构体（process_struct）之类的。这是因为 Linux 使用“任务”来表示执行的基本单位，而不是严格区分进程和线程。每个可独立调度的执行单元都用一个 task_struct 表示，因此这个数据结构中既包含进程信息，也包含线程信息。当然，示例的PCB结构体和Linux里的task_struct在调度时被视为同一个实体。另一个有趣之处在于，进程控制块包含指向父进程和子进程的 PCB 的指针。所以在我们的这个示例中，可以添加这个细节。

再次强调的是，进程控制块并不是一个进程，而是进程的一个状态表示，其中蕴含上下文的信息。它用作存放启动或恢复进程所需的所有数据，以及一些记账信息的存储库。而这个表示，就是实际放入内核空间中调度队列中的内容。 至此，我们已经准备好深入探讨 CPU 调度问题了。
