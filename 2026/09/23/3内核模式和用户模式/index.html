4T03 内核模式和用户模式

发表于2026-09-23|更新于2026-09-24
|浏览量:

我们学操作系统时，最早接触的一个概念是：操作系统是硬件和用户程序之间的中间层。也就是说，用户程序不能绕过操作系统直接访问硬件资源。

但仔细想想，操作系统和用户程序本质上都是软件，都是用编程语言写出来的。 那问题就来了：既然都是软件，为什么用户程序不能反过来压倒操作系统，自己接管整台计算机呢？这就引出了今天要讲的主题：硬件和软件如何配合，才能让现代操作系统既可靠又稳定。

在开始之前先说明一下： 视频里为了便于理解，做了很多简化。里面展示的实现方式或汇编代码，并不对应任何真实存在的平台或架构。

而“权限控制”这件事，恰恰是少数几个光靠软件本身解决不了、必须由硬件支持的问题之一。我们知道，每台计算机的处理器都有一套自己能执行的指令，叫指令集。如果我们想让一个软件比另一个软件拥有更高的控制权，可以定义一小组特殊指令，并且规定只有部分程序才能使用它们。很多架构里，这类指令叫特权指令。而要实现这种限制，硬件必须支持不同的运行模式——比如内核态和用户态。否则，光靠软件自己，是拦不住另一个软件的。

常见的方法是使用一个特殊的单比特的寄存器，该寄存器只能保存0或1。这个寄存器被称为模式位。当其值被设置为1时，处理器认为处于特权模式，意味着它可以执行指令集中的任何指令，包括特权指令。当其值为0时，处理器运行在受限模式，意味着它不能执行特权指令。

CPU 执行指令时，普通指令在任何模式下都能执行，模式位不参与判断；但特权指令能否执行，取决于当前模式位是否允许。于是关键问题来了：这个模式位由谁来翻转？ 如果用户进程能自己切到特权模式，那模式位就形同虚设。所以翻转不能靠普通指令完成，只能由硬件在特定事件发生时自动完成——这类事件就是进入内核态的入口，包括中断、异常和系统调用，包含中断、异常和系统调用。下面先以中断为例说明。

不过在讲中断之前，需要先厘清两组容易混淆的概念：内核态/用户态，以及内核空间/用户空间。它们是理解”模式位如何翻转”的前提。

内核模式（内核态）和用户模式（用户态）说的是 CPU 当前运行代码的权限等级：内核态拥有最高权限，能执行所有指令并访问全部内存和硬件；用户态权限受限，不能执行特权指令。而内核空间和用户空间说的是虚拟内存地址被划分成的两块区域：内核空间供内核使用，只有内核态能访问；用户空间供应用程序使用。

两者的关系是：态决定空间——CPU 处于内核态时可以访问内核空间和用户空间，处于用户态时只能访问用户空间。

这里容易产生一个误解：既然内核态能访问用户空间，那用户程序是不是有机会让 CPU 以内核态去执行自己写在用户空间里的特权代码？答案是否定的。因为进入内核态的合法入口只有中断、异常、系统调用三类，而这三类的目标地址都由内核预先设在内核空间里。也就是说，切到内核态和跳进内核空间，在入口处是同时发生的——一旦进入内核态，PC 就已经指向内核代码，用户程序根本没有机会让 CPU 以内核态去跑自己的代码，也就无法劫持操作系统。

需要区分的是：内核态代码在执行过程中确实可能回头访问用户空间（比如读写用户缓冲区），但这属于”内核代码以内核态访问用户空间”，执行的仍然是内核代码，而不是”用户代码以内核态运行”。两者不是一回事。正因为如此，特权指令只能由内核写好的、位于内核空间的代码来执行；用户程序能做的只是发起请求，由内核代它完成特权操作。

好，有了这两组概念，我们再回来看中断。下面先以中断为例，说明模式位是如何被翻转的。

程序正常运行时，PC 指向下一条要执行的指令，程序就这样一条条走下去。中断会打破这个流程：它像发给 CPU 的一个信号，通知某个事件已经发生，比如用户按下键盘或移动鼠标。

CPU 收到中断信号后，会暂停当前进程，自动切换内核态，然后查 IDT（中断描述符表，一个位于内核空间的数据结构）取出中断处理程序的地址，把 PC 重新指向它——也就是跳转到内核空间中执行中断处理代码。

PC 一旦指向中断处理程序的地址，接下来就是中断的处理流程（执行中断处理代码），大致可分四步：

首先，保存被中断进程的运行状态； 这里的保存并不是依赖 PCB 这种数据结构，而是通过 push 指令把信息压入栈中。由于此时 CPU 已经切换到内核态，使用的栈也不再是用户栈，而是内核栈（中断现场不会被用户程序篡改），等处理完毕后，再通过 pop 恢复现场，返回用户程序。

接着，执行中断处理代码。这里的处理代码并不是只有一种，而是每种中断各有一段（异常和系统调用是这样）。 因为事件种类不同，要做的事也完全不同。比如键盘中断要读键盘控制器，时钟中断要更新系统时间并检查调度，缺页异常要分配物理页并修页表，系统调用 printf 则要执行输出。这些逻辑没法用同一段代码处理，所以内核为每一种事件都准备了一个处理程序入口，这些入口统一登记在 IDT（中断描述符表）里，PC走不同地址的中断处理代码；

然后，处理完毕后恢复被中断进程的状态；

最后，执行一条特殊指令——中断返回（如 x86 的 iret），它同时做两件事：把 PC 跳回原进程，并把模式位切回用户态。

这就是中断的基本工作流程：它暂时中止当前进程，并将控制权转给内核当中的中断处理程序。

现在回到模式位：我们知道了中断不仅可以使程序计数器跳转，还可以自动将模式位的值反转位1（为了下一步立刻去内核查IDT）。PC指向内核空间时模式位都是1，这意味着内核地址下的程序永远是在特权模式下执行的。现代的做法就是确保操作系统被加载到此处，从而能够使用特权指令来完全控制系统。支持操作模式的处理器正是为此目的而设计的。特权模式专为内核当中的操作系统设计，受限模式专用于用户程序以防它们压倒操作系统。

现在我们来看内核模式可以完成、而用户模式不能做的几件事。

第一，直接操控 I/O 设备。 比如网络、显卡、硬盘驱动器，以及显示器、键盘等外设。用户模式不能直接操控这些设备，因为直接操控它们需要使用特权指令。

第二，操控 MMU，从而掌控内存。 特权指令允许操作系统操控 MMU，而 MMU 负责限制 CPU 可访问的物理内存区域。掌控 MMU 就意味着完全掌控内存。因此，操作系统可以读写任意物理内存位置，包括用户程序的地址空间；用户模式则不能。

第三，安全地使用中断机制。 CPU 收到中断后，必须跳转到中断处理程序。中断处理程序必须放在内核地址空间里，不能放在用户进程的地址空间里；否则用户进程可能覆盖它，从而劫持中断流程。操作系统通过特权指令加载 IDT，决定 CPU 收到中断后查哪张表、跳转到哪个内核入口；同时，因为 MMU 也由特权指令控制，内核地址空间对用户进程不可见、不可写。这样，用户进程既不能篡改 IDT，也不能覆盖内核里的中断处理程序，中断流程就完全掌握在操作系统手里。

以上就是用户模式程序无法执行操作中的几个例子。

不过，用户模式并非什么都不能做。用户程序仍然可以使用大量普通指令：在用户模式下，程序可以执行移动和复制数据等基本任务，执行算术、浮点和按位运算，进行条件判断和运行循环。但问题在于，日常所需的读取文件、在屏幕上显示文本、通过网络发送消息等基本操作，本身都依赖硬件。而用户模式又不能直接访问硬件，因此用户程序必须通过某种方式间接访问硬件。否则，用户程序能实现的就只是由普通指令构成的那一小部分功能，用途极为有限。那么，用户程序是如何间接访问硬件的呢？答案是系统 API。

你可能听过 API。在《SDK 的建立与引用》这篇文章里，我们把它简单描述为：SDK 库实现文件所对应的头文件中的函数声明。这里我们仍然沿用这个说法，但要做一点更精确的限定：这里的 SDK 库指的是平台 SDK。平台 SDK 的实现文件，是用于和硬件交互的 SDK 库；这些库所对应的 API，就是系统 API。操作系统以库的形式提供这组功能，目的就是让用户程序能够访问硬件资源。而这些 API，就封装了系统调用；用户程序调用它们时，会通过系统调用进入内核。系统调用就是前面讲的那三个内核入口之一。

例如，如果一个用户程序需要处理文件，它就需要通过系统调用 open() 来打开文件；每次想要读取或写入文件时，还需要更多的系统调用，如 read() 和 write()；当工作完成后，还需要另一个系统调用 close() 来关闭文件。

系统调用仍然是函数，这意味着它们必须具有内部实现，并且最终会被编译为机器码。但这里的情况开始显得有些奇怪：因为这些函数是库的一部分，当我们编写用户程序并使用这些函数时，它们会成为源代码的一部分。这意味着在编译后，它们会成为我们用户程序的一部分。然而，这并不合理，因为我们刚才已经确定，用户程序运行在用户模式下，因此无法使用操作硬件所需的特权指令。

那么，这里究竟发生了什么？

如果我们仔细观察，就发现在这些系统调用函数内部的某个时刻，存在一条触发中断指的令。是的中断不仅可以通过硬件触发（前面的CPU触发），也可以通过软件触发。

在这种情况下，int 指令会使程序触发一个中断，导致程序计数器跳转到操作系统地址空间中的一个例程。这个例程以内核态运行，可以执行操作硬件所需的所有特权指令，从而完成系统调用。在这个架构中，这个例程就是中断处理程序，所以在这里，系统调用可以理解为由库函数触发的一次特殊中断。

一旦所需的特权指令执行完毕，就必须将控制权返还给被中断的进程，并确保 CPU 恢复到用户模式，使程序能按预期继续执行。当然，具体实现因架构而异：在此示例中，这一步由中断返回指令 iretq 完成；但在其他架构中，系统调用跳转到的内核例程并不一定是中断处理程序，因此可能需要专门的指令来切换操作模式，或者显式修改模式位，然后再通过另一条指令把控制权返还给被中断的进程。

对前面这个矛盾，一种简单的解释是：系统调用函数的一部分位于用户模式运行的用户程序地址空间中，另一部分则位于操作系统的地址空间中并以内核模式运行。

这里我们来讲系统调用的优缺点。

系统调用最重要的优点，是它为开发人员提供了硬件抽象。许多人并不清楚直接操作硬件有多么困难和复杂，比如让 CPU 触发中断。由于系统调用替我们处理了硬件交互，当我们需要访问硬件资源时，作为开发人员，只需要调用它们即可，从而能够用代码思维而不是晶体管思维来思考问题。

另一个优势是安全性，这与硬件抽象密切相关。直接操作硬件容易出错，可能导致漏洞和系统故障。从 Python 或 JavaScript 这类解释型语言转向底层编程语言的人常常会问：我的语言特性会不会因为编写错误而烧坏我的电脑？例如下图：

图中是一个标题为“C 编程沙箱”的帖子，具体内容是：在 Linux 机器上写 C 程序，需要专门搭建一个“沙箱环境”吗？我担心自己犯内存分配之类的错误，把机器弄坏。我记得很多年前上大学时，在 Windows 上是用 NetBeans 配合一些工具来“沙箱化”运行 C 程序的。在 Linux 上也有必要这么做吗？如果需要，具体该怎么搭建？提前感谢。

答案当然是否定的，因为操作系统替我们管理硬件。即使我们编写了一个非常糟糕的 C 程序，也无法以可能损坏电脑的方式直接操纵硬件。

第三个优点是可移植性：如果多个平台遵循某些规范，同一份源代码就能在不同系统中编译。

系统调用也有一些缺点，第一个是性能开销，这在某种程度上也和与它们提供的硬件抽象相关。在我们的架构中系统调用是依赖中断的，但是它在性能上并不廉价。

首先，系统调用需要额外的步骤，例如用户态与内核态之间的上下文切换。这里的“上下文切换”是广义的：它指 CPU 从用户态进入内核态时，需要保存用户程序的寄存器现场、切换到内核栈、可能还要切换页表，处理完再恢复现场并返回用户态。它满足上下文切换的一般定义，但并不是 PCB、调度队列和切换例程所完成的那种进程上下文切换。后者是进程 A 被换下、进程 B 被换上；而这里只是同一个进程从用户态进入内核态，再返回用户态。

其次，现代 CPU 的缓存、TLB、分支预测器等机制会进一步放大这个成本。无论是系统调用、中断还是异常，CPU 都会突然离开用户程序，进入内核执行另一段代码。内核代码和内核数据会占用缓存，可能把用户程序原本的热点代码和数据挤出缓存；地址转换缓存可能被扰动，流水线也可能被冲刷。也就是说，扰动并不只来自系统调用，中断和异常同样会造成这种影响。这里之所以把它算作系统调用的缺点，是因为系统调用是用户程序主动发起的：用户程序为了请求内核服务，不得不进入内核，也就不得不承担这次进入内核所带来的缓存扰动成本。

此外，程序执行系统调用指令后，控制权就交给了操作系统。一旦操作系统获得控制权，就无法保证它会立即处理这个系统调用。操作系统可能先利用这个机会执行其他任务，比如运行 CPU 调度程序来决定是否切换到另一个进程（也就是调度器基于调度队列选出下一个进程，再由切换例程保存和恢复 PCB，完成进程间切换），或者管理其他系统资源。

虽然系统调用最终会被处理，但对于用户程序来说，无法保证处理会很快发生。

图：底层开发者被系统调用的硬件抽象吸引，钻进了它带来的巨大性能开销陷阱…

另一个缺点是平台依赖性，这与我之前提到的可移植性优点相矛盾。尽管许多平台都力求兼容，但某些奇怪的差异仍然存在。

例如，Windows 的内核函数并不采用 Unix、Linux 和 macOS 所兼容的函数形式。

总结一下 CPU 操作模式：用户程序可以通过中断指令 int 0x80 使 CPU 切换到内核模式，但代价是中断自身，并将 CPU 控制权交还给操作系统。反过来，操作系统可以使用特权指令 iretq 恢复被中断的进程，但强制其继续以用户模式运行。

由于系统调用的概念非常成功，一些架构开始提供专用指令，让系统调用更容易发起。例如，不再需要由系统调用封装函数去执行 int 0x80 这类中断指令，而是可以直接使用专门的系统调用指令。因此，在许多架构中，你可以找到 syscall 指令和 sysret 特权指令。

其中，syscall 由用户程序执行，用于从用户态进入内核态，发起系统调用；sysret 由内核执行，用于从内核态返回用户态，恢复用户程序继续运行。它们分别对应传统方式中的 int 0x80 和 iret，但路径更短、更专用，也让汇编代码更易读。

不过，这种“用户程序主动发起系统调用，才能进入内核”的机制，也带来一个问题：如果用户程序一直不发起系统调用，操作系统还有机会重新获得控制权吗？

当操作系统依赖用户程序主动协作来重新获得控制权并执行管理任务时，它被归类为非抢占式或协作式操作系统。这类操作系统已经不再被使用，因为它们存在一个重大问题

设想一个包含无限循环且内部没有任何系统调用的程序。CPU将无限期地陷入执行该循环。

如果一个进程有意或无意地避免使用系统调用，CPU 将永远不会将控制权返回给操作系统，实际上使所有其他进程陷入饥饿。这种情况下，仅靠软件无法解决问题，必须依赖硬件支持。

解决方案是定时器。当定时器到期时，它会触发一个硬件中断。该定时器通常是 CPU 外部的独立硬件，或集成在芯片组/SoC 中，但只能通过特权指令控制。在将 CPU 分配给用户进程之前，操作系统会设置定时器；程序运行时，定时器开始倒计时。

当一个进程在定时器到零之前使用了系统调用，CPU 会进入内核态执行系统调用处理程序。操作系统可以在内核里暂停或重置定时器；在返回用户态之前，再重新设置定时器，让它重新开始倒计时。如果一个进程长时间不调用系统调用、不主动让出 CPU，定时器到期后会触发时钟中断，强制 CPU 进入内核态，让操作系统重新获得控制权，并由调度器决定是否换进程，如果决定切换，就由调度器决定换哪个进程，再由切换例程操作 PCB，完成进程上下文的保存与恢复。

该机制使内核能够完全控制每个进程允许使用的 CPU 时间。这算是补充了前面内核模式能够完成的几件事的内容。

此外，当 CPU 支持操作模式时，硬件必须能够响应用户程序试图直接操作硬件的行为，而不仅仅是拦截它。如果处理器在用户模式下运行并遇到特权指令，硬件可以配置为立即触发一个异常——也就是我们前面提到的进入内核态的合法入口之一的异常——将控制权交给操作系统，以便它立即处理用户程序的可疑行为，通常是终止其执行。这类由当前指令直接引发的同步事件，通常被称为异常或陷阱，以区别于键盘、网卡、时钟等外部设备发出的异步硬件中断。

当硬件支持这种完整的中断机制，尤其是时钟中断和异常中断时，这种系统就被称为抢占式操作系统。

说到这里，我们已经解释了：在用户程序和操作系统本质上都只是软件的情况下，操作系统是如何取得对用户程序的控制权的。用户程序被限制在用户模式下，无法直接与硬件交互，必须把控制权交给操作系统，由操作系统代为完成。

因此，“操作系统始终处于用户程序和硬件之间”这一说法，其实是对真实情况的一种高度抽象。

许多人想知道，除操作系统之外的软件是否也能在内核模式下运行。答案是能，典型例子就是驱动程序。当新的显卡发布时，操作系统往往不知道如何控制它，因为操作系统在显卡出现之前就已经开发出来了。而操作系统开发者也不可能为每一种可能存在的硬件设备预先编写代码。因此，这项任务通常由硬件制造商完成。解决方案称为驱动程序，是专为控制特定硬件而设计的软件。由于控制硬件需要特权指令，驱动程序必须在内核模式下运行。当用户程序需要硬件时，操作系统会使用相应的驱动程序。

然而，让驱动程序在内核模式下运行也带来了一个严重缺点：操作系统允许在内核模式下运行的代码——包括驱动程序，以及后文提到的反作弊软件和恶意软件检测软件——都可以执行特权指令，而且它们共享同一个内核地址空间。因此，操作系统无法像隔离用户进程那样，把这些代码与其他进程、甚至与操作系统自身完全隔离开来。

如果一个驱动程序错误地写入了错误的内存地址，就可能破坏操作系统的关键数据；如果驱动程序崩溃，整个操作系统也会随之崩溃。操作系统崩溃后，用户程序无法运行，进而导致整个计算机系统崩溃。

这样是为什么有缺陷的驱动常常导致Windows蓝屏死机。尽管存在风险，允许代码在内核模式下运行仍是必要的，因为驱动程序不可或缺。

至此，我们已经了解了驱动程序为什么必须在内核模式下运行。在此基础上还可以进一步说：在操作系统支持的前提下，第三方代码也能在内核模式下运行。这样一来，内核模式下的第三方代码就不再局限于设备驱动程序，还可以用于其他用途，比如视频游戏的反作弊系统和恶意软件检测软件。

以内核模式运行的软件有两个明显优势：第一，它不依赖系统调用，因此运行速度比在用户模式下快得多；第二，它可以直接监控硬件活动。

以游戏反作弊为例：想象一款禁止使用手柄、以防止对鼠标和键盘玩家造成不公平竞争的游戏。玩家可能通过第三方程序将手柄映射为键盘来作弊。由于游戏运行在用户模式下，它无法判断输入是否真的来自键盘；而以内核模式运行的反作弊软件可以直接监控硬件活动，检测输入是否来自真实手柄。

而对于恶意软件检测，内核模式允许软件扫描网络适配器等设备，监控网络流量，并检查正在运行进程的地址空间，以发现可疑行为，例如监视私人数据并将其发送到不可信的终端。

现在就很清楚为什么这类软件必须在内核模式下运行：如果它们在用户模式下运行，就无法完成这些任务。不过，并非所有情况都适合用内核模式。

以CrowdStrike为例，这是一款安装在全球数百万企业设备上的恶意软件检测软件。

2024年7月19日，一次更新损坏了一个配置文件，导致文件内容全部变为零。文件损坏后，该软件崩溃，导致操作系统也随之崩溃。

结果是全球范围的大混乱。成千上万的设备出钱蓝屏死机，企业遭受了数十亿美元的损失。

另一个例子是 Vanguard。

它是拳头游戏公司为《英雄联盟》和《瓦洛兰特》开发的反作弊软件。因为要直接监控硬件和系统底层，它运行在内核模式下。

首次发布时，Vanguard 曾导致数百名玩家的电脑出现蓝屏死机。这正好说明，内核模式代码一旦出错，就可能拖垮整个系统。

但更让人担忧的是它和腾讯的关系。腾讯是拳头游戏的母公司，也在中国代理这两款游戏。你不安装 Vanguard 就无法玩拳头游戏，这从反作弊角度看是合理的；但问题是，Vanguard 即使在你不玩游戏时，也仍然以内核模式运行。这意味着，它理论上可以监控你在电脑上的所有操作。

目前没有证据表明 Vanguard 确实这么做了。但腾讯作为一家中国公司，因为受到中国政府监管，有人担心中国政府可能通过腾讯，要求它配合获取用户数据或监控用户，这就引发了隐私方面的担忧。考虑到 Vanguard 安装在全球数百万台电脑上，这种担忧就变得更让人不安。

但讽刺的是，CrowdStrike 和 Vanguard 这类第三方内核软件，运行环境是微软的 Windows；而 Windows 本身也在收集大量用户数据，本身就是一个间谍软件。
