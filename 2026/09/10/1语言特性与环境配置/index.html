编辑器的时代转变与集成程度

一 记事本（古早编辑器）时代的工作流

回到“记事本写代码”的时代，一个完整的编程工具链，至少由三个独立部分组成：

编辑器（如记事本）：负责查看和编写源代码（如 .cpp 或 .java 文件）。

编译器：将源代码编译成可执行文件。

运行器：执行编译后的程序

这里需要说明一下：

我们引入了“运行器”这个概念，似乎和之前学习 C/C++ 时的知识有冲突。 当时我们认为：运行是把编译后的机器码发给操作系统，执行运行的是操作系统本身，没有什么“运行器”这个概念。 但是，运行器对于 C/C++ 来说就是操作系统，对于 Java 来说不是。 所以我们特化出“运行器”这个概念，用来区分每种语言的“运行者”的不同。

配置要求

除了操作系统自带的记事本（编辑器）之外，你需要自行下载并安装编译器和运行器。

工作流程

用记事本打开 .cpp 文件，编写代码并保存。

手动找到编译器的目录，执行编译命令，生成可执行文件。

再手动找到运行器，执行该文件。

每一步都是独立操作，没有集成。

二 现代编辑器时代的工作流（以 VSCode 为例）

VSCode 本质上是一个现代化的编辑器，和记事本一样，它没有内置编译器和运行器。 但它相比记事本，多支持了一类工具：

智能报错 / 辅助插件：提供语法高亮、错误提示、代码补全等功能。

配置要求

因为 VSCode 只是一个编辑器，你需要额外配置：

编译器（如 JDK 中的 javac）

运行器（java 命令）

智能辅助插件（如 Java Extension Pack）

要让它能够开发 Java，你需要手动添加这三样东西。

工作流程（与记事本的核心区别）

现代编辑器不仅多支持了智能插件，还集成了调用入口：

你可以在编辑器里写代码，点击工具栏的 “编译” 和 “运行” 按钮。

这些按钮背后调用的仍然是你手动安装的编译器和运行器，但你无需离开编辑器界面。

这就是 “集成”的核心含义： 编辑器会自动执行记事本时代的 保存 → 编译 → 运行 流程，从而简化了手动操作。

VSCode 的定位：可以变身成 IDE 的轻量级编辑器

VSCode 本身不算 IDE，因为 IDE 要求“开箱即用”，而它需要你自行安装插件和工具链。

但由于它可以被配置成具备 IDE 核心功能（代码补全、编译、调试等）， 我们通常说：VSCode 是一个“可以变身成 IDE 的轻量级编辑器”。

理解 VS（IDE）与 VSCode的集成程度区别

什么才能叫 IDE（集成开发环境）？ 关键在于：是否将编辑器、编译器、运行器、调试器、智能辅助等工具集成在一个界面中，且下载后即可开箱即用。

Visual Studio：✅ 符合，是完整的 IDE。

VSCode：❌ 不符合，集成了调用入口,但是没能做到开箱即用,所以是一个可以变身为 IDE 的编辑器。

那为什么还要用 VSCode 开发 Java？

因为 Visual Studio 对 C++ 支持极好，但对 Java 生态中许多特定库、框架（如某些轻量级 Web 框架、特定构建工具）的支持较弱。

VSCode 轻量、灵活、插件丰富，通过手动配置后，可以针对 Java 项目获得一个更可控、更模块化的开发环境。

配置 Java 环境感觉复杂的原因 并不是因为 Java 语言本身更难，而是因为 VSCode 这个编辑器需要你手动组装这些组件。

JAVA的语言特性

C、C++ 是静态编译语言：在运行前，源代码直接被编译成当前平台能执行的机器码文件（如 .exe）。

Java 是动态编译语言：在运行时，才把字节码即时生成机器码执行（JIT）。

这个说法在工程交流中没问题，但从编译原理角度看，不够准确，甚至掩盖了 Java 更本质的设计。

要理解这个本质，我们得先回顾几个基础概念：

1什么是动态编译、什么是静态编译语言？

2前面提到的字节码到底是什么？——这又引出了 Java 的跨平台特性

1 从C++的“运行时多态”看“静态编译”与“动态行为”的边界

在学习C++的面向对象时，我们其实已经接触过“编译时”与“运行时”的区别： private 关键字的作用是，将一个函数调用“推迟”到运行时再决定具体调用哪个函数，从而让虚函数表的替换成为可能，最终导致程序执行与编译时看起来“静态绑定”的结果完全不同。

这表明：C++ 虽然整体是静态编译语言，但已经具备少量“运行时决定调用”的能力。 只是这种能力被严格限定在“多态”这一特定场景下，远没有达到“改变整个程序编译模型”的程度。

而Java，则把这种运行时灵活性，从“语言的某个特性”扩展到了“整个编译模型”的层面。 要理解Java这种独特的编译模型，就必须先了解它实现“一次编写，到处运行”的基石——跨平台特性背后的架构。

2 Java 的跨平台特性后的编译模型：不是“动态编译”，而是“双阶段编译”

Java 的跨平台能力来源于一个中间产物：字节码（.class）。

字节码不是机器码，而是一种统一格式的中间表示。

运行阶段，JVM 会根据当前操作系统，把字节码编译成对应平台的机器码，因此可以做到“一次编译，到处运行”。

那 JVM 到底是什么？ JVM 本质上是一个“运行器”，但它内置了内存管理、类加载、安全沙箱等能 力，比 C++ 的运行器要做的事情多得多，所以被称为“虚拟机”。 但要注意：这个“虚拟机”和我们平常认知中的虚拟机（如 VMware、 VirtualBox）含义完全不同。

JVM 这类“进程虚拟机”：只模拟程序的执行环境，实际运行仍依赖本机操 作系统

VMware 这类“系统虚拟机”：模拟的是整台电脑（包括 CPU、内存、硬盘、 操作系统等） 所以 JVM 虽然叫“虚拟机”，但它并没有真正模拟一个完整的操作系统，它 的核心作用更接近于 “字节码 → 机器码的翻译器”。

回到编译模型本身，真正的运行过程是：

编译阶段（javac-java的编译器）： 源码 → 字节码文件（静态编译，发生在运行前）。

运行阶段（JVM-java的运行器）： JVM 把字节码再编译成当前平台的机器码（即时编译 JIT，发生在运行时）。

这就是双阶段编译：

第一阶段：静态编译（.java → .class）

第二阶段：动态编译 / JIT（.class → 机器码）

在实际交流中，很多人认为第二阶段更特殊、更重要，于是默认忽略了第一阶段，只强调第二阶段，直接把 Java 称为“动态编译语言”。 这其实是对双阶段编译模型的简化说法，偏离了本质定义。

3 Java 的“部分编译”能力：不靠 IDE，靠编译模型

Java 有一个非常实用的工程优势：可以在不改动整个程序的情况下，只重新编译部分文件。

优势的根源：

Java 编译器不是生成一个巨大的单体字节码文件，而是为每个类生成一个独立的字节码文件（.class）。

一个 .java 源文件可能包含多个类（例如一个公共类加几个内部类），编译后会生成对应个数的多个 .class 文件。

示例：

一个 Java 程序由 A.java 和 B.java 组成：

A.java 中定义了 3 个类（A1、A2、A3）

B.java 中定义了 1 个类（B1）

示例：

修改代码的情况：

修改 A.java（比如改了 A1 类），不修改 B.java。

只编译 A.java：

bash

javac A.java

生成 新的 A1.class、A2.class、A3.class（覆盖旧的），保留原来的 B1.class

✅ 程序依然可以正常运行

这就是“部分编译”，更严格的叫法是”增量编译”：

不需要重新编译整个项目

大大减少了重复编译时间

不依赖任何 IDE 优化，是 Java 编译模型天生支持的

4 为什么 C++ 做不到同样的部分编译？

C++ 的编译模型不同：

每个 .cpp 被编译成 .o（目标文件）

所有 .o 必须经过静态链接，最终生成一个完整、单一的 .exe 文件

这个 .exe 是一个整体，无法单独替换其中一部分

因此，在“记事本时代”手动管理编译时：

修改一个 .cpp

你需要重新链接整个 .exe

无法像 Java 那样，只替换一个 .class

结论：C++ 的手动工作流中，不存在与 Java 等价的部分编译。

那 C++ 的‘预编译头’不是也能实现部分编译吗？

C++ 的“预编译头”是工具优化，不是语言特性

现代 C++ IDE 引入了预编译头（PCH）：

把不常变的大段头文件（如 windows.h）一次性编译成中间状态

只要这些头文件不变，就不再重复编译

可以显著减少重复编译时间

但请注意：

预编译头是 IDE / 构建工具的工程优化

它并没有改变“C++ 必须静态链接成单一可执行文件”的本质

也就是说，它没有解决“手动无法实现部分编译”的缺陷

预编译头和 Java 的“部分编译”是两个层面的东西，不能混为一谈。

关于部分编译 一个常见的错误归因

很多学艺不精的人会这样认为：

“Java 能部分编译，是因为它是动态编译语言。”

这是错的。

正确的逻辑是：

Java 能实现部分编译，是因为：

双阶段编译 → 存在中间表示（字节码）

多中间文件 → 每个类独立生成一个 .class 文件

而 C++：

没有双阶段编译

最终产物是单体 .exe

无法替换局部文件

所以 Java 的部分编译能力，是编译模型 + 文件组织策略的结果，不是“动态编译”带来的。

5 Java 与 C/C++ 运行器的调用与交付区别

5.1 回到“运行器”概念

回到上一节刚引入运行器概念的时候，我们说过：

一个完整的编程工具链由编辑器、编译器、运行器三部分组成。 但在 C/C++ 里，运行器其实就是操作系统本身——双击 .exe，操作系统直接加载机器码执行，没有什么独立的“运行器”程序。

我们之所以要抽象出“运行器”这个概念，是为了统一描述**“谁负责让程序最终跑起来”**。

5.2用户运行 Java 程序需要额外安装运行器 对于 C/C++ 是操作系统，对于 Java 则是  JVM

C/C++ 的 .exe 发给用户，用户直接双击就能跑，因为操作系统自带“运行器”。

Java 不行。用户如果想运行 .class 文件，必须先安装 JDK（里面包含 JAVA运行器JVM以及它依赖的运行库）。 也就是说，Java 的运行器不是操作系统自带的，需要用户额外下载。

这里需要澄清一个概念：Java 运行时环境（JRE） 确实就是用户运行 Java 程序所需的最小集合，仅包含 JVM 和 运行库。 理论上，用户只需要安装 JRE 就够了。

但在实际操作中，从 JDK 11 开始，Oracle 不再提供独立的 JRE 安装包，第三方发行版也大多直接提供 JDK。 加之 JDK 安装包本身并不大（约 150–200 MB），对普通用户来说完全可接受。

因此，与其纠结 JRE 和 JDK 的区别，不如直接让用户安装 JDK，省事、统一、不易出错

调用运行器的两种方式

无论哪种语言，运行程序通常有两种方式：

5.3为什么 Java 不能用方式一？

因为 Java 编译器生成的是多个 .class 文件（每个类一个），而不是一个单体可执行文件。 双击 Main.class，操作系统不知道如何加载其他依赖的 .class，所以无法运行。

这是 Java“多中间文件”编译模型的直接后果

5.4那Java 程序（字节码文件）怎么让用户简单运行？

你可能会担心：普通用户（或者说“小白”）很可能不会用命令行去调用运行器，总不能让每个人都去下载一个编辑器，再把文件夹加载进去，然后手动点那个绿色的“运行”按钮吧？

——其实完全不用这么麻烦。

Java 提供了 打包（JAR） 机制：把所有 .class 打包成一个 .jar 文件，并指定入口类。 用户双击 .jar 文件（前提是系统关联了 java -jar），就能运行。

5.5那为什么开发时默认不打包成 JAR？

因为开发过程中，你经常要修改单个类 → 只编译那个类 → 立刻运行测试。

如果每次都要先打包成 JAR，流程就变成了：

text

修改 A.java → 编译 A.java → 重新打包 JAR → 运行

这会拖慢开发节奏，也破坏了 Java 的“部分编译”优势。

所以开发时直接用 java Main（方式二）调用运行器，打包成 JAR 是发布给用户时才做的事

总结：

对于普通用户来说，运行一个 Java 程序（纯 .jar 文件）确实需要：

电脑上已经安装了 JVM（通常通过安装 JRE 或 JDK 获得）

双击 .jar 文件（前提是操作系统已将 .jar 文件关联到 javaw.exe 或 java -jar 命令）

这就是 Java“一次编译，到处运行”的代价：用户必须自己装运行器。

但是这也有一个好处：因为 JDK 中包含了 JVM 及其运行库，所以用户不会遇到类似 C++ 程序中那种“缺少运行时库”的问题

Java 开发/运行版本与 JDK 的关系

1. Java SE：JDK 直接提供的就是 Java SE

Java SE（Standard Edition） 是 Java 的核心平台。 你从官网下载、安装的 JDK，对应的就是 Java SE 开发环境。

装 JDK = 获得完整的 Java SE 开发/运行能力。

2. Java EE：在 SE 之上附加的企业级能力

Java EE（Enterprise Edition） 是一套企业级 API 规范（如 Servlet、JPA、JMS 等），用于开发 Web 应用、微服务、大型分布式系统。

Java EE 不是一个独立版本的 JDK，而是建立在 Java SE 基础之上的扩展能力。

要开发 Java EE 应用，需要三步：

装好 JDK（获得 Java SE 的运行环境）

在项目中引入 Jakarta EE 依赖（如 jakarta.servlet-api）

配合应用服务器（如 Tomcat、WildFly）来运行

Java EE 不需要重新安装另一个 JDK，同一个 JDK 可以直接用来开发 Java SE 或 Jakarta EE 项目。

只有当你需要用 Java 开发服务器端应用（Web 后端、API 服务、企业级系统）时，才会用到 Java EE（Jakarta EE）的规范。如果只是写普通的桌面程序、命令行工具或基础逻辑，Java SE 就完全足够了。

而刚刚提到的应用服务器就是一套“成品”的运行环境，你的 Web 程序（.war 文件）部署到里面，就能直接跑起来。 它已经实现了 Java EE / Jakarta EE 的各种复杂规范，你不用自己从头写这些底层的网络通信、事务管理、数据库连接池等，直接调用它提供的 API 就行。
