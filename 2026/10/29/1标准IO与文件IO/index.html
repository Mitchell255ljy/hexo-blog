1T01 标准IO与文件IO

发表于2026-10-29|更新于2026-10-29
|浏览量:

我们在 4T03《内核模式与用户模式》中提到过系统调用的四个实例：open()、read()、write()、close()。它们都是与文件操作相关的系统调用，属于文件 I/O 接口函数。之所以要通过系统调用来完成文件操作，是因为文件系统本身属于内核空间的子系统，用户态程序无法直接访问，必须借助系统调用陷入内核，才能由内核代为完成相关操作。

标准 I/O 则是在文件 I/O 的基础上提供了缓冲区。之所以需要这层缓冲，是因为系统调用的开销相当大：从用户态到内核态的一次模式切换，不仅涉及硬件层面模式位的转换，还伴随上下文保存与恢复、参数校验、权限检查、内核路径解析、文件偏移更新、页缓存交互等一系列操作，需要耗费大量时间与资源。相比之下，真正执行具体事件的中断处理代码本身占用资源很少，开销主要来自这次跨越用户态与内核态的切换过程。

为了优化这一点，我们可以在用户空间引入缓冲区，把多次小规模的系统调用合并为少数几次大规模的系统调用，从而减少用户态与内核态之间来回切换的次数。标准 I/O 库（如 C 标准库中的 fopen()、fread()、fwrite()、fclose()）正是这一思路的体现：它不再让每个标准 I/O 函数都直接对应一次系统调用，而是在用户空间维护一个 FILE 结构体，其中包含缓冲区的基址、当前读写位置，以及剩余/已攒字节数等成员，由这组函数围绕这块缓冲区完成读写。

缓冲区大小由编译期常量 BUFSIZ（默认 1024 字节）决定，所有 FILE 共用同一个值，因此不必在结构体中记录缓存区的大小。缓冲区本身是在 fopen() 中通过 malloc 创建的：每调用一次 fopen，就新建一个 FILE 结构体和一块独立的缓冲区，一个 fp 对应一种状态标识（_READ 或 _WRITE）和一块专属缓冲区。正因为每个 fp 的缓冲区物理上相互独立，且同一时刻只按一种模式（读或写）操作，所以不存在多个 fp 共用一块缓存、或对同一块缓存又读又写的问题，标准 I/O 的逻辑因此得以成立。

LINUX上的标准IO实现

在展示具体的实现代码之前，我们需要先明确一个概念：结构体里即将出现的 fd（文件描述符）到底扮演着什么角色。

文件描述符（file descriptor，简称 fd）是内核分配给进程的一个非负整数，用来标识该进程打开的一个 I/O 资源（例如普通文件、管道、套接字、I/O 设备等）。

这也就是《并发的底层支持》中所说的：从进程切换的角度看，一个进程包含 CPU 状态、进程的地址空间、一组打开的文件，以及分配给它的 I/O 设备。其中，“一组打开的文件”和“分配给它的 I/O 设备”在 PCB（进程控制块，Linux 中为 task_struct）中主要就体现为文件描述符表。简单来说，文件描述符表就是内核用来专门存储和管理这些 fd 的数据结构。

在 PCB 结构体内，这个文件描述符表实质上是一个指针数组。数组里的每个指针，都指向内核中全局的“打开文件表项”（struct file）。而 fd，本质上就是这个指针数组里某个位置指针对应的索引（下标）。

当我们调用 open() 成功时，内核并不是直接给你返回一个空的 fd。它的内部动作是：先在这个数组里找一个空闲的位置（比如下标为 3），然后在内核全局区创建并初始化一个“打开文件表项”（记录着读写偏移量、读写模式等），并将其指向底层的物理资源（如普通文件、I/O 设备、管道或套接字等）。最后，内核把这个“打开文件表项”的内存指针填入数组的第 3 号位置，完成这步真正的数据绑定后，才把下标 3 作为 fd 返回给用户程序。

因此，fd 并不是一个内存地址，它只是存放在 PCB 结构体内部数组里的一个“取件码”。用户拿着这个 3 去调用 read()/write() 时，内核会顺着当前进程 PCB 中的文件描述符表，找到下标为 3 的指针，进而定位到内核全局的打开文件表项，最终操作其指向的底层物理资源。这也解释了为什么一个 fd 标识的其实是一个“打开对象”，且多个进程可以拥有相同的 fd 值，但它们各自 PCB 里的描述符表会指向完全不同的底层文件或 I/O 设备。

C 标准库中的 FILE 结构体，则是在文件描述符之上的一层用户态封装。 FILE 内部通常包含一个文件描述符（即代码里的 fp->fd）、一块用户空间缓冲区（fp->base），以及读写位置（fp->ptr）、剩余字节数（fp->cnt）等信息。fopen() 会先通过 open() 从内核取得一个 fd，再在用户空间分配并初始化一个 FILE，把该 fd 存入其中，并准备好缓冲区。此后 fread()、fwrite() 等标准 I/O 函数先操作 FILE 中的缓冲区，只有在必要时（如缓冲区满或关闭文件），才用其中保存的 fd 去调用 read()、write() 等系统调用。

在每个逻辑分支后接了一个 flags（状态标识”们”），令它等于几个宏的按位或运算的结果。这几个宏分别对应一个数字，都是在二进制表示中只有一位为 1 的数字，比如十进制的 1、2、4、8、16。这样它们进行按位或得到的数字，在二进制表示能在每一位上记录信息。也就是说，一个结果数字十进制为 5（二进制 101），只能是由 100（十进制的 4）和 1（十进制的 1）或运算得到的。如果 4 和 1 分别表示两种属性的话，那么 5 就能表示这两个属性都被启用了。

在我们的 my_fopen 示例条件判断分支中，涉及的宏分别代表的属性和十进制下的数字为：

r 模式：只读打开（O_RDONLY，十进制 0）

w 模式：只写打开 + 不存在则创建 + 打开时清空（O_WRONLY | O_CREAT | O_TRUNC，十进制 1 | 64 | 512 = 577）

a 模式：只写打开 + 不存在则创建 + 追加到末尾（O_WRONLY | O_CREAT | O_APPEND，十进制 1 | 64 | 1024 = 1089）

2.fgets（字符串输入） fgets 从文件流中读取一行，它同样是循环调用 fgetc。但为了保证安全，它有两个限制：最多只读 size - 1 个字符，且遇到换行符 \n 就停止，最后再手动补上一个 \0：

在这里我们有一个发现： 为什么 fgets 必须有额外的停止处理（一旦 fgetc 获取到 \n 就立刻 break），而 fputs 却没有类似的逻辑去提前识别 const char *s 里有没有 \n，如果有就立刻终止输出呢？

原因在于输入和输出对 \n 的语义处理完全不同：

对于输入侧（fgets）：遇到 \n 停止（break）是为了满足“读取一行”的业务需求。停止循环后，剩余的输入数据依然安全地留在内核或底层 FILE 缓冲区里，等下一次读取。这属于应用层的逻辑截断。

对于输出侧（fputs）：绝不能遇到 \n 就终止输出。因为字符串是放在内存里的，如果随意终止，会导致后半截数据直接被丢弃，造成输出不完整。

但这并不意味着 fputs 对 \n 毫无特殊处理。 为了与 fgets 的“读取一行”形成完美的对称，输出侧的 fputs 把对 \n 的处理逻辑下放到了底层。也就是说，输出侧遇到 \n 不该是逻辑上的截断，而应该触发一次物理刷新——把当前用户态缓冲区里攒的数据立刻推给内核，让用户马上看到这一行。

这个刷新机制不在 fputs 这一层，而在底层的 fputc 内部。在我们前面写的 my_fputc 示例中，还没有体现这一点（它只会在 1024 字节满了才刷新）。但在真实的 C 标准库中，fputc 内部确实有“遇到 \n 立刻刷新”的逻辑。这个下放到底层的实现机制，就是我们下一节要详细补充的——行缓冲（Line Buffering）机制。

缓冲刷新问题

从算法竞赛中因缺少 flush 导致的交互式测试锁死，到 C/C++ 底层行缓冲与全缓冲的切换机制，这些现象本质上都属于同一个核心问题：缓冲刷新问题。

我们分两部分来剖析这个问题： 第一部分，从算法竞赛的视角出发，看看不同交互模式（非交互式 vs 交互式）下，刷新机制为何会导致死锁； 第二部分，深挖底层机制，拆解标准 I/O 在不同环境下的缓冲行为（行缓冲、全缓冲），以及 C/C++ 标准库是如何用代码实现它的。

第二部分:行缓存和全缓存

在前面的标准 I/O 模拟实现中，我们的 FILE 结构体和 my_fputc 代码其实是不完整的——它们只知道往缓冲区里塞数据，只有塞满 1024 字节才会触发系统调用。

但实际在 Linux 环境下运行对应程序时，我们观察到的现象却并非如此简单：

如果只写 printf(“1234”);（没有换行），程序不输出 1234，这是符合预期的。

而在字面量末尾加上 \n，变成 printf(“1234\n”);，就正常输出了。

这就无法解释为什么在终端上 printf(“1234\n”) 即使没写满也能显示（而且不是像前面提到的那样，由程序退出时强制刷新缓冲区触发显示）。

为了搞清楚这些现象，我们需要改变一下 FILE 结构体和 my_fputc 示例代码，让它能够根据 fd 绑定的类型不同（终端还是磁盘文件），区分行缓冲和全缓冲的行为。但在此之前，我们需要先明确标准 I/O 的三种缓冲模式：

行缓存：和输出到终端设备相关的缓冲区叫做行缓存，行缓冲区的大小为 1024 字节，其中会接收到 \n 和写满缓冲区而进行系统调用，对应的文件指针：stdin、stdout

全缓存：和输出到磁盘文件相关的缓冲区叫做全缓存，全缓冲区的大小为 4096 字节，只在写满缓冲区时触发系统调用，对应的文件指针：fp

不缓存（Unbuffered）：和标准错误相关的流。它的本质是根本没有分配用于攒数据的缓冲区（而不是分配了 0 字节的内存）。数据一产生就直接推给内核。对应的文件指针是：stderr。这样做是为了保证程序崩溃时，错误信息能第一时间输出。

现在，我们用刚才改造的底层逻辑以及 printf 的实现，来解答最初遗留的疑问：

第一个问题：为什么 printf 不加 \n 常常不输出，加了 \n 就立刻输出？

这是因为 printf 默认将内容输出到终端，属于标准的行缓冲模式。通过看它的底层实现就能明白，它内部其实就是封装了 fputc（也就是我们上面刚改造完的带行缓冲判断逻辑的代码）：

当我们写 printf(“1234\n”) 时，字符 \n 会触发底层 fputc 中的行缓存刷新机制，立刻把缓冲区的数据推入内核，所以马上就能看到输出。

当我们只写 printf(“1234”) 时，没有遇到 \n，缓冲区也没满，数据就暂时滞留在了用户态的 stdout 缓冲区里，导致终端上“看起来什么都没输出”。

第二个问题：为什么没写 \n，程序退出时也能输出？ 回顾我们在第一部分讲“非交互式题目”时提到的机制：当 main 函数返回、程序正常退出时，标准库会自动 flush 所有还开着的缓冲区。所以即使 printf(“1234”) 没有触发 \n，程序在结束时也会把 1234 强刷入内核。

双输出流cout的实现与缓冲机制

为了搞清楚同步模式下 cout 到底是怎么把数据写出去的，我们先来看它的完整调用链（如下图）：

streambuf 可以理解为“另一个版本的 stdout”，或者是 FILE * 的两个不同实例，分别叫这俩名。既然是不同实例，那么它们就占用不同的缓冲区，因为两个 fp 使用 open 系统调用肯定不是同一块内存，然后 streambuf 的 fd 也是绑定到终端设备的。

按理说这两个互相独立，完全可以分着用；但是 streambuf 默认和 stdout 同步。也就是说，streambuf 一直在把自己的数据转交给 stdout，而不是写进自己的缓冲区。

具体来说，同步模式下，流程图展示了完整的调用链：

1.cout << “hello” 调用了重载的 operator<<；

2.进而调用 streambuf 的 sputn / sputc；

3.但在同步模式下，streambuf 并不自己攒数据，而是将 stdout 这个 FILE * 当作参数，逐个字符调用标准 I/O 的 fputc(c, stdout)；

4.数据最终进的是 stdout 的缓冲区；

5.最后由 stdout 根据它的模式决定什么时候调 write 系统调用（比如缓冲区满、遇到 \n 或手动 flush）。

注意这里的行缓冲：因为数据走的是 stdout 的缓冲区，而 stdout 在连接终端时默认是行缓冲的，所以同步模式下，遇到 \n 依然会触发系统调用刷新。

所以同步模式下，streambuf 自己的缓冲区其实是空着的，数据都走 stdout 那条路。这样就会慢一些，因为你每次都要经历“转交 stdout → 调 fputc”这一套，比直接写自己的缓冲区多几步。这个开销导致的单次时间消耗不大，但是在算法竞赛等高输出场景中，关闭同步让 cout 用自己的缓冲区，会明显节约不少时间。

同步带来的好处与关闭同步的后果

同步模式带来了一个明显的好处：cout 和 printf 可以混用，且保证混用时按顺序输出（因为二者最终的数据都汇聚到了 stdout 这一个缓冲区里）。

那如果把同步关了（ios::sync_with_stdio(false);）会发生什么呢？此时 streambuf 不再把数据转交给 stdout，而是写进自己的独立缓冲区。此时它不再是行缓冲，而是全缓冲——只有缓冲区被填满、或者显式 flush（如 endl）时，才会真正触发 write 系统调用。所以关闭同步后，\n 不再保证触发刷新。

而且因为 printf 和 cout 分别用不同的 fp，分开刷各自的缓冲区，没有同步机制保证顺序，所以输出顺序就不确定了：

终端驱动缓冲与scanf cin的实现

我们在终端上进行输入时，当前行的内容就属于终端的终端驱动缓冲区。这里的内容是为了让你修改当前的内容，支持回退，直到用户按下 \n 确认当前行的输入，才会把终端驱动缓冲区的内容刷入内核。

这里有一个极其容易混淆，但又必须讲清楚的概念： 终端驱动的这个机制，本质上也是一个“行缓冲”。 它和我们前面讲的 fputc 行缓冲逻辑是一模一样的，因为都是遇到 \n 就把数据输出（推）给内核。但是，它们俩绝对不能混淆，因为它们的作用是不同的。

1标准 I/O 的行缓冲（fputc）：发生在用户态。程序把数据塞进 FILE 缓冲区，遇到 \n，就把数据推给内核（调用 write）。

2终端驱动的行缓冲：发生在硬件/系统驱动层。键盘输入的内容先攒在终端驱动缓冲区，遇到 \n，就把数据推给内核。

既然机制一样，为什么绝不能混淆？因为它们所在的层级和目的完全不同：

标准 I/O 的行缓冲：纯粹是为了减少系统调用的次数（避免一个字符就调一次 write）。

终端驱动的行缓冲：纯粹是为了支持人类用户的退格和修改。你敲错字了，没按回车前，数据攒在驱动里让你改；按了回车，才正式提交。

类似于printf的scanf的实现链

scanf 走 vscanf 解析格式串，然后内部封装 getc，这个流程到最后也是利用 stdin 这个 fp。

输入路径分三层：

第一层：终端驱动缓冲

行缓冲，遇 \n 才把整行交给内核

作用：支持行编辑（退格、修改）

用户没按回车前，数据一直攒在这里

第二层：内核输入队列

终端驱动按回车后，把整行数据放到这里

read 系统调用从这里读数据

第三层：stdin 的 FILE 缓冲

没有行缓冲，触发条件是缓冲区空了就 read

read 从内核输入队列读一批进 stdin 缓冲

scanf / getc 从 stdin 缓冲逐个取字符

看到这个路径，你可能会问：既然输入也有缓冲区，为什么 scanf 不需要配备 flush？ 因为“刷”这个动作根本不是它做的——输入侧的行缓冲由终端驱动执行，scanf 只是被动地从 stdin 缓冲区取字符。

搞懂了输入侧的三层结构后，我们再把目光转向输出侧，就会遇到第二个问题：为什么输出侧不体现三层结构？

你可能会疑问：既然 cin 和 scanf 的输入路径有三层，那 cout 和 printf 正好是它们的反向，按理说输出侧也应该有三层才对。为什么输出侧不体现三层结构？ 这是因为，输入侧有严密的“消费逻辑”和“按行确认”机制，而终端驱动对输出的态度是“来了就收”，完全不攒着等条件。 具体体现在以下两点：

第一点：终端驱动对输出没有“消费等待”行为

在输入侧，终端缓存驱动会配合 getc 触发严格的“消费”逻辑（也就是从缓存区取数据，取空了就向内核要）：

这是典型的“取一个，cnt 减 1，减到 0 就 read 下一批”。而输出侧的终端驱动完全没有这套逻辑：内核把数据推给终端驱动，然后终端驱动直接渲染到屏幕，不攒、不计数、不等条件。

这就导致了“内核到终端”的内核中间层被直接忽略。因为输入时内核的数据会滞留，而输出时不会，所以我们看不见内核层。

第二点：终端驱动对输出不需要“行缓冲” 输入侧的终端驱动之所以要做行缓冲，是为了支持回退和修改（用户敲 123，发现错了，退格改成 124，再回车，数据攒着才有编辑机会）。 而输出侧终端驱动不需要行缓冲，也不支持回退操作，所以我们直接忽略了输出的终端驱动层。

综上，输入侧因为层层攒数据、等条件，三层结构清晰可见；而输出侧是直达的，故三层结构就看成了一层结构。

终端单个字符读写getchar 与 putchar

getchar 和 putchar 内部固定使用的就是标准输入 / 标准输出（stdin / stdout）。它们几乎没有任何对 fgetc / fputc 的封装——不处理字符串（不像 fgets / fputs 那样套一层循环逐个读写），也不处理格式（不像 scanf / printf 那样要加格式串解析）。说白了，就是把一个变量交给 fgetc / fputc，只不过 fp 固定是 stdin / stdout：

格式化文件读写fprintf fscanf

格式化文件读写

因为 printf 和 scanf 这两个格式化读写默认走 stdout 和 stdin，是绑定了终端的。而我们有 fprintf 和 fscanf，这两个格式化读写比 printf 和 scanf 不一样的是，多了一个实参，这个实参就是标明要写向的 fp。因为自由的 fp 的文件描述符可以为一个文件，故能作为向文件的格式化读写操作。

函数原型对比

字符串（包括格式串）转char数组

sprintf

得到的 str 就是 format 对应的内容。

第一个参数 str：目标转化后的数组，用来接收结果。

第二个参数 format：格式串，传递的时候直接传格式串的名称（字面量或数组名）即可。

剩下的参数 …：格式串里 %d、%s 等格式控制符对应的参数，按顺序一一对应。

当 format 是不含格式控制符的普通字符串时，就没有 … 参数了，这个函数就退化成了”普通字符串转成 char 数组”；否则就是”格式串转成 char 数组”。

snprintf

sprintf 有个安全隐患：小的 char 数组接不了大的 format 内容。如果真的用小数组接大内容，编译能通过，但运行时会触发 RE（运行时错误 / 越界）。

于是就有了 snprintf：

snprintf(char *str, 长度, const char *format, …);

第二个参数的数字表示从头部开始最多转化的长度。

但这玩意本身并不会提前帮你防 RE——填的数字如果比目标数组能容纳的还大，照样会接不住。所以这个数字应该配合 sizeof(str) 或 str.size() 使用，不能随便填一个数。

广泛的标准IO函数

到这里，我们已经把标准 I/O 的家族看了一大半。先来回顾一下我们看过的内容：

四个系统调用：open、close、read、write。

基于系统调用封装的单字节文件读写：fopen、fclose、fgetc、fputc。

基于 fputc 和 fgetc 封装的字符串文件读写：fputs、fgets。

单字节终端读写：getchar、putchar。

指向终端的格式化/终端读写：printf、scanf、cout、cin（通过标准文件指针 stdout/stdin）。

指向外部文件的格式化读写：fprintf、fscanf（比 puts/gets 多支持了格式串解析）。

字符串转 char 数组：sprintf 与 snprintf。

我们现在跳出文件 I/O 的范畴，单看标准 I/O 的全局，其实无非就是两件事：

向外部文件进行：字符串（含格式串）读写 + 单个字节读写。

向终端进行：字符串（含格式串）读写 + 单个字节读写。

可以说是非常全面了。剩下那些涉及 I/O 操作的函数，基本上是重复功能的，只不过在特定的细节场景下应用不同。比如我们下面要讲的模块化读写。

模块化读写

fwrite/fread的功能

这俩就是指定读写很多字节的文件 IO 操作，相当于 fgets / fputs 吗？

功能上像，但本质不同。

我们前面已经详细剖析过，fputs 和 fgets 实际上就是循环调用 fputc 和 fgetc 来实现的。它们在底层逻辑上会“筛去”空字符：

fputs：循环条件是 while (*s)，也就是遇到 \0 就立刻停止。后面的字节全丢。

fgets：遇到 \n 停，并且会在读出的字符串末尾强行补上一个 \0。如果我们用它读出的数据本身包含 \0，这个强行补的 \0 就会扰乱原始数据。

所以，当我们读写包含空字符（\0）的数据（比如二进制文件，空字节是有实际意义的）时，绝对不能使用 fputs。在操作这类不可省略空字节的文件时，必须使用 fread / fwrite。

而且关于前面讲的 fprintf 和 fscanf 也是多了一层格式串逻辑解释的 fputs / fgets，这个也是同样的道理——它们都按“文本/字符串”语义处理，遇到 ‘\0’ 或格式边界就停，不适合搬二进制。

fread / fwrite 的实现

fread / fwrite 不是套壳 getc / putc，它们另搞了一套实现，直接操作 FILE 缓冲，用 memcpy 搬块：

fread / fwrite 不是套壳循环调用 getc / putc，它们是在 FILE 缓冲之上另搞了一套“搬块”实现。 和 fgets / fputs 功能上像，但本质不同：fgets / fputs 按字符串语义处理，fread / fwrite 按字节块原样搬。

std::string 与 const char *

在 C 当中我们是没有这个类型的，字符串对应的默认格式为 const char *。而且字符串绑定 const char * 这个属性，广泛地应用于很多函数接口作为实参。所以我们要区分 std::string 类型和 const char * 类型的字符串。

std::string 类型是一个 class 来声明的类型。这个 class 类里写了很多方法，类似于这样：

我们 std::string 声明的对象都可以调用这些子函数。这些子函数是操作 std::string 类型的方法的，而不是 C 下的 const char * 字符串（比如 find、erase、+= 追加等）。

而如果你想要用 C 字符串的功能函数，就是 strstr、strcpy 这样的。但要注意，不管是 C 风格的 const char * 还是 C++ 的 std::string，它们在内存里都强制要求以 ‘\0’ 结尾。

const char * 强制要求 ‘\0’：因为 C 语言函数（如 strlen、strcpy、printf）没有单独的长度参数，只能顺着内存往后找，直到遇到 ‘\0’ 才知道字符串结束。

std::string 也强制要求 ‘\0’：虽然它内部自己维护了长度（size()），计算长度不依赖 ‘\0’，甚至中间可以包含 ‘\0’，但 C++ 标准强制规定：std::string 底层分配的内存末尾必须有一个 ‘\0’。这纯粹是为了兼容 C 语言，方便你调用 .c_str() 时能无缝接给 C 函数。

C 字符串常用函数（操作 const char * / char *）

1求长度：strlen

遇到 ‘\0’ 停止，返回字符个数（不含 ‘\0’）。

2拷贝：strcpy / strncpy

strcpy 把 src 拷进 dest，包括末尾的 ‘\0’。dest 必须足够大，否则越界。

3查找子串：strstr

在 haystack 里找 needle，返回第一次出现的指针，找不到返回 NULL。

1. std::string 转 const char *

用 .c_str() 

.c_str() 就是把 std::string 内部的字符数组指针提取出来的一个函数，让 p 指向它。

但是会有个问题：指针 p = str 指针，是浅拷贝。

也就是说，指针拿的是 str 串的地址值，而 str 地址值指向的内存若被清除了，只有地址值是没有用的。也就是说，p 会因 str 的生命周期而消失。当一个 std::string 实例超出了生命周期时发生析构，p 就变成了悬空指针（毫无价值）。

而且，不仅是析构，只要 s 发生修改导致内部重新分配内存（比如追加长字符串），p 也会立刻失效。

我们这里有个解决方案：strcpy。这个函数就是把 C 风格字符串（const char *）转成独立的 char 数组。这样，我们既可以把内容拷贝到 char 数组里长久存起来用，也可以在需要时临时用掉。

const char * 转 std::string

直接赋值或构造函数，会自动进行深拷贝。

为什么是深拷贝？ 因为 std::string 类内部写好了两样东西：

包含参数的构造函数：string(const char* s)，用来接收 C 字符串并申请新内存拷贝。

重载了 = 运算符：string& operator=(const char* s)，让赋值操作也能自动拷贝。
